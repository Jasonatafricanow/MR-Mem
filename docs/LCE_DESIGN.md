## 0. 要解决的问题

**目标：知道就是知道，不知道就是不知道。不知道是一种合法状态，不是缺陷。**

| 状态 | 含义 | 例子 |
|---|---|---|
| 有证据 | 原文里说过，当前有效 | "我住在里斯本" |
| 过时 | 曾经为真，后来被更新 | "住在波尔图"（后来搬了） |
| 错误 | 从来不成立：被用户纠正，或推断被否认 | "我没说过要辞职"；A+B→E 被否认 |
| 无法确认 | 有相关证据，但证据本身定不了 | 计划没有结果；转述；冲突未澄清；说得含糊 |
| 没说过 | 记录里根本没有 | 问从没聊过的事；问题带着错误前提 |

- 这五种是系统要**达到的效果**，不是要给每个查询算出一个标签返回。实现方式见 §5.2 的对应表。
- 现状：基线把每条消息平等地存进去，按相关度最多返回 100 条，这几种情况在读出时长得一模一样。实测返回条数一多，拒答题从 65 分掉到 35 分：回答模型把"沾边"当成了"知道"。

### 0.1 术语（全文、代码、提示词都以此为准）

| 术语 | 含义 | 不要再用的说法 |
|---|---|---|
| 原文 | 唯一权威 | — |
| SB（SemanticBlock） | 避免断章取义的最小完整意思（§4.1）。在 Line 上的 SB 也叫"一步" | block、node、point 混用 |
| 承接 | SB 之间的边："这一步是在那一步的基础上推进的"（§4.2） | 默认接上一块、话头相接 |
| Line | 事件或思想逻辑的推进过程，由 SB 和承接边构成，去中心化（§4.3） | 分支、主干、一件事、matter、容器 |
| 摘要 | SB 本身就是对原文的一种摘要（用户 10-16），不再对 SB 做摘要。Line 级的概括先不做（§4.4） | Line 的名字、编译时吸附内容的容器 |
| 晨昏线 | 当前时间：SB 所说的事在它之前已发生或冻结，还是仍在进行。它扫过整张图，同一条 Line 上一部分步骤在暗侧、一部分在亮侧（§4.5） | — |
| Thread / Path A | Line 上处在进行时 / 过去完成时一侧的部分（§4.5） | 两个容器、"搬进 Path A"、"这条 Line 是 Thread 还是 Path A" |
| Path B | 由过去推出的未来时可能性，跨 Line 的可证伪假设（§4.8） | — |
| 维度 | 观察角度，没有高低 | 层级、纵向/横向 |

讲解里用过的纸箱、葡萄牙旅行、买电脑、鸡蛋、git/commit、平行时空、翻页都是**比方**，只用来帮助理解，不是概念，也不要写进提示词当示例。

## 1. 原则

1. **原文是唯一权威，原文之上全是投影。** SB、Line、治理字段都是编译或推导的产物，都可能理解错，也都可以纠正。纠正产生新的不可变状态，旧状态保留，可审计、可回放。原文不可改；只有系统级的人工删除才删原文（如用户要求删除数据）。原文丢失时，投影保留并标灰，不隐藏。
2. **时间才是确定性。** 一件事发生了，状态才锁定；计划、意图、承诺说得再确定也没有发生。
3. **时间流逝不构成发生的证据。** 计划的时间过了，冻结的是"当时有过这个计划"，不是"它发生了"。
4. **推断可以回滚，原文和历史不删。**（§3.3）
5. **不推断自己没见到的。** 只基于已经到达的内容，没有未来函数。
6. **一次推理，不付两次钱。** 指对话本身的理解推理：在线时，Body 回复用户的那次推理顺带产出 SP；之后切 SB、连线是再次推理确认，复用仍在上下文里的 KV 缓存，以很低的成本整体理解再切分。它不是说"每批消息必须一次调用填完所有字段"。离线测试集可以整体读取再切分（§4.7）。
7. **读出只做减法和事实标注，不加指令，不合成答案。**（§5）
8. **自下而上：先有 SB 和承接，Line 是连出来的。** 写入时不预设主干、分支或"属于哪件大事"。

## 2. 时间：只有双时间轴

| 时间 | 含义 |
|---|---|
| `occurred_at` | 消息发生时间：这条原文在历史上的位置 |
| `known_at` | 发现时间：系统什么时候得到它、可以使用它；派生状态有自己的 `derived_known_at` |

- 实时对话里两者相同，只在补录旧记录时分开。不加第三条时间（不加 `event_time`、`due`、`time`）。
- **内容里说到的时间是内容，不是时间轴。** "十年前去过冰岛"里的时间原样留在内容里。编译器把能确定的相对时间换算成固定格式，写在原话旁边，如"明天晚上（2024-05-07 19:00）"。"过没过点"就是拿内容里的这个时间和当前时间比较（`TenseStore.side` 从内容里读）。换算不了的模糊时间不写固定格式，交给语义上的 `settles` 判断。
- **SB 的时间（用户 10-16）。** 每条原文保有自己的 `occurred_at` 和 `known_at`。内容里有具体时间就如实记在内容里；没有前后贯穿几条消息的，就用那条消息明确的发生时间；前后一段时间里的一段行为，用首尾消息的时间段（存进 Line 节点已有的 `occurred_start` / `occurred_end`）。SB 的 `known_at` 是它被编译出来的时间；窗口收口后才编译，所以按 `known_at` 回放时不会提前看到结果。
- **数据源没给消息时间时**：系统不编造 `occurred_at`，只保留先后顺序；读出和编译输入里都不写消息时间。但内容里说到的时间（"2024 年去过北京"）照样保留。
- **当前时间（晨昏线的位置）从哪来**：
  - 当前读出：取查询时间；离线评测集取该用户最后一条消息的时间。
  - 历史回放：取指定的回放时点，同时过滤掉 `known_at` 晚于它的记录。
  - 没有消息时间的数据：以接收时间（`known_at`）为当前。内容里说的 2024 年的事，在 2026 年收到时已在当前之前，按晨昏线冻结是对的（用户 10-15 01:13 确认）。**【待确认】**外部 v8 写的是"无时间戳时禁用按时间冻结"，和用户 10-15 的确认相反，需要用户定。
- 一切"最近""到点"都按消息时间算，不按系统时钟，回放是确定的。

## 3. 状态的三层

三层互相独立，任何一层的变化都不能推出另一层的变化。

### 3.1 事实状态：由证据驱动

- 认知方式复用核心已有的 `EpistemicStatus`（断言、计划、不确定、假设、反事实、转述、未知）和 `TemporalScope`，由编译器在 SB 级给出。不新造枚举。
- 关系复用核心已有字段：
  - 取代（`supersedes_memory_id`）：旧值过时；
  - 矛盾（`contradicts_memory_ids`）：未澄清时两边的证据都保留，但不等于同一时点两个互斥的断言都成立；澄清后转为取代；
  - 支撑。
- 计划和结果不新增关系：它们是 Line 上的先后步骤。

### 3.2 推断状态：由 LCE 负责

`UNRESOLVED` 是 LCE 对自己推断的判断（"这几块证据该连成什么结构，我定不下来"），不是对事实的判断，不能拿来当"无法确认"用。一条 Line 可以很确定（"用户计划明年去葡萄牙"），而"去没去"本身仍无法确认。

### 3.3 被否认的推断：撤销、保留、可重评

否认分两种，处理不同：

| 用户说的 | 否认的是什么 | 处理 |
|---|---|---|
| "这两次点便宜外卖不代表我抠门" | 推导：A+B 不足以支持 E | 撤销 E 当前的有效性，依赖它的结构回到上一个仍有依据的状态；写入拒绝记录"A+B 不支持 E"。同样的证据下不得再生成 E；后来出现新证据 C，A+B+C→E 可以重新评估 |
| "我根本不在乎性价比" | 结论 E 本身 | 同样撤销并写入拒绝记录；这句话本身还是一个用户断言的 SB（非 E）。之后出现零星新证据，也不能自动复活 E，除非有证据表明用户的偏好后来变了（取代关系） |

- 回看历史时，被否认的 E 仍可审计；按 `known_at` 回放，否认之前它仍然可见。
- **拒绝记录只有一处，在 MR-Mem。** 拒绝记录保存被否认的对象、依据和适用范围。编译时把相关拒绝记录和候选步骤一起交给编译器，精确匹配作最后一道闸（LLM 换个说法就能绕过纯精确匹配）。
- 回滚的是当前有效的认知；否认本身作为新事实追加进历史，不抹去任何记录。

### 3.4 注意力：这次编译有没有读到

- 注意力只决定编译时编译器能看到哪些已有步骤（§4.6），**不改变事实和推断**。衰减只改变注意力，不改变真实性。
- 休眠就是这次没被读到。睡了一年的 Line 在读出时照样能被查询召回，不会因为睡着就被当成放弃，也不会被当成已经发生。

## 4. 核心模型

### 4.1 SB：避免断章取义的最小完整意思

```
原文（唯一权威）
  └─ MR-Mem 编译 → SB，以及 SB 之间的承接
       └─ LCE（总称），三部分并列：
            ├─ Thread：进行时状态的 Line
            ├─ Path A：过去完成时状态的 Line
            └─ Path B：由过去推出的未来时可能性（可证伪）
```

- LCE 是总称。说整体就写"LCE"，说某一部分就写明是哪一部分；不要用"LCE"代指 Path A。
- **SB 跨多个 turn。** 一个提问、对它的回答、紧接着把意思补完整的追问和澄清，合起来才是一个完整的意思。不要把问和答、一句话和它的补充切成原子碎片。
- **一条消息可以分进几个 SB（用户 10-16）。** 人的一次回复常常按几个点纠偏、指正，各点说的是不同的事，每个点各成一个 SB。没有显式写成 1、2、3 的也一样。例如"你到额度了提醒我啊，就在那里傻等啊？现在 agy 可用了。但是我觉得你这数据情况来看并不好啊"里是三件事：没报警、agy 恢复、数据不好。
- **一个 SB 里同时有已发生和未发生的部分时，切成两个**："约了明天吃饭"切成"约了"（已发生）和"明天吃饭"（未发生，有时间）。
- **保留谁说的、谁接了谁的话、谁没有搭理。** 互动信号本身就是信息，不能把所有人的观点放成同一权重。
- **状态说的是那件事，不是那句话（用户 10-15）。** 提问、请教这个动作不构成"进行中"；计划和没做完的工作是进行中；决定、做完的、观察到的是已发生。
- **字段可以留空，不为填满格式而过度解读。** 不要把随口一句硬套成"关键转折"。

**两种场景，SB 装的东西不同（用户 10-15～16）：**

- **工作场景**（人和 Agent 一起做事，尤其是编程）：人是决策主体，内容是项目的真实进度和问题管线。LLM 会制造大量噪音，真正的推进很慢，还要反复纠错。
  - **SB 的形态（用户 10-16 晚）。** 实际交互里，人是跟着 Agent 的汇报来做决策的。所以：
    - **需求 SB**：session 开头人提出的原始需求是一个 SB。之后人提出的、不来自 Agent 汇报的新需求，也按语义各成新的需求 SB。
    - **QA SB**：之后每一步是一组"Agent 提出情况或问题 → 人给出反馈"。前半是 Agent 这一轮带来的：做了什么、遇到了什么问题、报告了什么结果、提了什么方案或问题；后半是人的反馈：决定、纠正、追问、评价（"怎么这么久？"）。一个 SB 读起来就是"遇到了什么 → 人怎么决定的"。
  - **只用当时能知道的。** 人做出决定的那一刻，不知道 Agent 之后会怎么实施；"从后面几轮读出结果、记进这一步"只有整库一次导入才做得到，没有意义。人决定之后 Agent 怎么执行、结果如何，是下一个 QA SB 的前半，用承接接回它回应的那一步。
  - **不重复录入。** Agent 的一次汇报只记在回应它的那个 SB 里，后面的 SB 用承接指向它，不再抄写。
  - **人一条消息里回应了几个点，就是几个 SB**，每个配上 Agent 汇报里它所回应的那部分。
  - Agent 只是提议或解释、没被人回应的内容，不单独成为 SB。Agent 做了很多事、没有推进原本那个需求，仍在同一个情况里。
  - **新需求不混进原来的 Line。** 判断它和已有步骤有没有承接，不看说了什么，看做了什么：后续实际的发展推进的是不是原有那件事。
  - **状态按当时已知**：人的决定、Agent 已报告做完或出错的，是已发生；Agent 汇报里还在跑、没出结果的，是进行中，等后面的 SB 交代了结果再用 `settles` 定下来。几件事并行都没结果时，它们都可以是进行中。
- **聊天场景**（人与人聊天，或用户向助手问答，比如 AML 测试集）：交互本身就是内容。助手的回答和推荐是用户得到的信息，标明出处记下；人与人的对话里，各人的立场和口味都是内容。一段经历可以切成几个 SB（做了什么、为什么、观察到什么、怎么想）。

### 4.2 承接：SB 之间的边

- **承接的意思是"这一步是在那一步的基础上推进的"**，推进的可以是事件，也可以是思想逻辑（用户 10-16：Line 是事件或思想逻辑的推进过程）。
- 承接可以指向很久以前的一步，可以有几个，也可以没有。
  - 工作场景里最常见的承接，是"输入 → 反馈或决策 → 输出，然后循环"：上一步的结果成了下一步的问题。但这只是常见情况，不是定义。
  - 一个想法接回很早以前的一个设定（比如"晨昏线"接回"进 Path A 就是 commit"），也是承接。
- **承接不等于因果。** "准备换电脑""最近预算紧张""暂时不换了"，第三步可以同时承接前两步，但不代表预算就是原因。因果只有原文说了才写进 SB 内容；取代、矛盾用 §3.1 的字段表达。
- **话头相接、时间上重合都不是承接。** 下一句接着说、同一时段发生（"后台测试在这期间跑完了"），都不构成承接。
- **没写承接就不连。** 代码里不能有"默认接上一步"的兜底。
- 代码只接受指向更早位置的编号（STEPS 里的 `N<k>`，本次输出里更前面的 `b<k>`），所以图不会有环；无效编号丢弃并记日志。

### 4.3 Line：事件或思想逻辑的推进过程

- **Line 由 SB 和承接构成（用户 10-16）。** 编译时只做承接，不先认定"这属于哪件事"。
- **去中心化。** 没有根、没有主干、没有 main。
  - 任何一步都可以长出几条 Line：到了葡萄牙之后，吃饭、逛街、买东西并列长出去；"想买电脑"可以长出涨价了、工资没发、旧的还能用。
  - 几条 Line 也可以在一步上汇合：两人"爱看电影"在"推荐电影"汇合。
  - 分叉出来的各条 Line 地位平等，没有哪条是"原来那条"。
- **子任务关系是长出来之后回头看出来的（用户 10-16）。** 为了编辑语义，我让你上网查研究路线、做提取语料的实验、找公共测试集，这三条都承接编辑语义那一步。但哪条走得远，当时不知道，所以不能假设什么是主干；在微观结构里区分主干，就是在预测未来。清洗语料那条走远了，冻结了，接下来的编译工作接回"编辑语义"那一步，因为它推进的是那件事，而不是上一步。长出来以后，宏观上才看得出它们都是编辑语义的子任务。
- **Line 永不结束，没有"结束"的概念。** 一步冻结只是它到了晨昏线的另一侧；从它还可以继续长。编译器不判断"这件事结束了没有"。
- **不同维度在 SB 上交汇。** 同一个 SB 可以同时在几条 Line 上，并且会随时间在别的维度上和别的 Line 产生关联：清洗语料现在是为了测试；将来它可能成了自我理解的素材。维度是观察角度，没有高低。不预设"纵向/横向""话题层/分支层"。
- **长成时间线不是问题。** 时间是逻辑发展的强 alpha 因子，只要不是强行按时间顺序接。
- **不是每个 SB 都要上线。** 聊开发时插一句"鸡蛋真好吃"，这个 SB 单独放着。
- **新长出的步骤只带指向它承接那一步的索引**，不背前面的全部内容。回溯时顺着索引往上走，不做全库检索。
- **不去界定 Line（用户 10-16 晚）。** 两条 Line 可以在一个 SB 上交叉，之后再分开，就像两条线相交，不需要合并，也不需要决定交点"属于"哪条。只有连续多个点重合，才说明两者实质上是同一段推进。去划定"一段 Line 从哪到哪"、去管它们合不合并，仍然是在试图定义线。
  - 代码底层只存 SB 和承接构成的图（允许多父多子），Line 是顺着承接走出来的推进过程，不是要先划界再存的对象。
  - 现状差距：`LineGraphStore` 给每个 SB 记了所属 line，`MemoryThread` 是编号 + 摘要 + 最新一步，两者都带着"先定义线"的痕迹，points 模式下也不建 `MemoryThread`。怎么清理，按本条另议。

### 4.4 Line 没有名字；摘要用于检索定位

- Line **没有名字**。名字当身份，事情一变名字就对不上；当检索，名字定死后事情走远了就搜不到（葡萄牙之旅后来改去西班牙和北非）。
- **SB 本身就是一种摘要（用户 10-16 晚）。** SB 已经是对原文的最小语义理解单位，不再对 SB 做摘要。检索和读出可以直接落在 SB 上，再顺着承接取前后的步骤。
- **Line 级的概括先不做（用户 10-16 晚）。** 不界定 Line（§4.3），它没有固定的挂靠对象；检索直接命中 SB。以后要做，也只是回头补写的检索辅助。被取代的旧计划在任何描述里都写成"已被取代"，不写成当前状态。
- **摘要不能做成一个吸附一切的全貌。** 实测（v8、v9 的开发会话编译）：编译时让模型凭摘要判断"这批内容在推进哪件事"，并且每窗重写摘要，结果一件大事的摘要越写越大，把后面所有内容吸进去，40 多步排成一条直线。
- 编译前检索候选：用新内容直接检索已有的 SB（SB 本身就是摘要），把命中的步骤交给编译器连到具体的步骤。不让模型对着任何概括判断归属，也不每窗重写概括。
- **改了方向仍是同一条 Line**：截止日变了、范围收了、目的地改了，都接续原来的步骤；否则旧计划一直挂着，被检索出来就会制造幻觉。**字面相似不代表推进的是同一件事**：不能因为都有"安排"就串在一起。
- 以后又想发展以前定下的事（不买电脑之后又想买），从那个已冻结的旧步骤继续长，对照当初的理由；旧步骤不改。
- 过去的步骤只在"对过去的认识"变了时才产生新修订（后来的证据表明当初理解错了、推断被否认），旧修订保留，历史只追加。

### 4.5 晨昏线：Thread 与 Path A 是 Line 的两种状态

- **Thread 就是处在进行时状态的 Line，Path A 是过去完成时状态的 Line（用户 10-16）。** 不是两个容器，SB 不在两者之间"搬家"。
  - 天黑了（已发生、已冻结、改变不了）= Path A；
  - 天亮着（还在进行、还可能改变）= Thread。
- **晨昏线扫过整张图，不是给整条 Line 贴状态（用户 10-16 晚）。** 就像地球同一时刻一半白天一半黑夜，同一条 Line 上，已发生、已冻结的步骤在暗侧，还在进行的步骤在亮侧。"Thread 是进行时状态的 Line"说的是 Line 上处在亮侧的那部分；问"这条 Line 整体是 Thread 还是 Path A"是错的问法。
- 区分的是时态："我想去葡萄牙"（意图）/"我去葡萄牙"（进行中，航班可能延误、改降、返航）/"我去过葡萄牙"（真的到了，在当下锁定）。
- **一个 SB 在哪一侧，由当前时间决定，不靠谁去改它：**
  - 说的时候就已经发生的：一直在过去一侧。决定在说出的那一刻就是已发生的事实，带着理由，不挂着等结果。
  - 未发生、有明确时间的（"明天 19:00 吃饭"）：时间一过就冻结。冻结的是"当时有过这个计划"这件事本身，不管后来发生没有；"没赶上、改签了"是从这一步继续长出来的步骤。
  - 未发生、没有时间的（"想买电脑"）：只有后来的内容让编译器读出它已定下来（"旧电脑还能用，不买了"）时，才用 `settles` 冻结。
- **有明确时间的真实世界计划会演化**：发生了什么就如实记下，接着往下长。没发生的就是没发生，不预先穷举各种可能。

### 4.6 编译时做什么、看到什么

- **编译顺序：先整体理解，再切 SB，最后连承接（用户 10-15）。** 先切 SB 再拿碎片逐个判断，会丢掉整体语义。同一次调用里分三步：
  1. 读这批原文（连同上下文和候选步骤）整体，看清它推进了什么；
  2. 切 SB；
  3. 每个 SB 写出它承接的已有步骤（`after`，可以多个，也可以没有）、说出时是否已发生（`happened`）、让哪些进行中的步骤定了下来（`settles`）。
- 承接、是否已发生、是否定下来，都由编译器（LLM）在上下文里读语义判断。**这是显性工作，不用向量互近邻、证据收敛、Pareto 来决定**（那些是 Path B 的工具）。
- **一次编译看到的是这个角度、这一阶段的全貌（用户 10-16）。** 维度没有高低。把不同维度的全貌混在一起，就会出现一件"大事"把所有内容吸进去。编译器不判断"这属于哪件大事"，那和分主干一样是在预测未来。
- **候选步骤（KNOWN_LINES）**：
  - 最近仍在进行的步骤。**没有时间的意图和计划就让它休眠，不每次都塞进候选（用户 10-16 晚）**；新内容和它相关时，靠检索唤醒；
  - 最近的步骤；
  - 用这批新内容检索唤醒的步骤（直接检索 SB，见 §4.4）；
  - 相关的已冻结步骤；
  - 相关的拒绝记录。
- 每个候选带一个短编号（`N3`），编译器用编号指代。编号由代码按位置分配，模型输出里的编号只当本次的局部引用；编号到代码 ID 的映射和编译结果一起记入日志，可以回放。
- 休眠 = 这次没被选进候选。它仍在，读出时照样可以被查询召回。

### 4.7 编译窗口与成本（用户 10-15）

- **窗口既不能一次读完全部，也不能硬切。** 上下文太长，模型会生拉硬套产生幻觉。所以有上限，但是**软上限**：到了目标量，往后找最近的**自然断点**收口。另有一个远大于软上限的硬上限。单条超长输入按章节、段落切，相邻块有重叠。
- **自然断点是一个 SB 完整收口的地方（用户 10-16 晚）**，窗口在这里切开不会把一个 SB 劈成两半：
  - 会话结束、长时间间隔；
  - 工作场景：人给出反馈之后、Agent 下一次汇报之前。一组"情况 → 反馈"在同一窗里收齐；Agent 后来的执行和结果属于下一个 SB（§4.1），不需要等。
  - 聊天场景（用户向助手问答）：助手回答完、人下一次开口之前（沿用 10-15 的设定）。
- **没说完的尾巴留到下一窗。** 编译器可以说"最后这几条还没讲完一步"（`carry_from`），这几条不切，带进下一窗一起切。
- **上一窗的原文作为只读上下文（CONTEXT）带进来**，只供理解，不能被引用、不会被重复编译；只有本窗的新消息（NEW）会产出 SB。
- **成本靠 KV / 前缀缓存，不靠每窗从头读。** 提示词按"稳定前缀 + 追加"排列：最前面是固定的编译说明，中间是该用户的原文（只往后追加，读过的部分就是缓存前缀），最后才是每次会变的部分（本次的新消息范围、候选步骤、拒绝记录）。缓存能不能被不同调用共享，取决于具体模型和服务，要实测。
- **翻页 = 开新对话 = 压缩。** 前缀累积到软上限、又走到自然断点时翻页：新前缀只放固定说明、压缩后的状态（相关的关键步骤，即 SB）和上一页末尾一小段原文。压缩是有损的，不保证与读完整原文的理解等价。
- 编译时关掉模型的思考模式。软上限、页大小这些数值用样例定。

### 4.8 Path B：未来时的可能性（第二阶段）

- 从多条 Line 的过去时里，推出跨经历的连贯假设。例如：看到喜欢的电脑没钱不买 → 点外卖纠结半天选了便宜的 → 每月生活费八千，看起来不是真没钱 → 推测更在意实用和性价比 → 选手机时推荐小米。
- **证据资格**：Path B 取用步骤时，必须带上它的认知方式（`EpistemicStatus`）和是否已发生。过点但没有下文的计划只能当"曾有意向"的证据，不能当"做过"的事实。
- **可证伪**：后来发现用户也很看重便利和美观，这条推断就被证伪或部分证伪，按 §3.3 处理。
- 跨 Line 的交汇点和背景索引就是它要用的关联。LCE 原有的结构发现（互近邻轨迹、证据收敛、Surface、灵感素材）属于这里，第二阶段移植。

## 5. 读出：交给回答方的东西

### 5.1 AML 规则下的边界

| 做法 | 判断 |
|---|---|
| 返回 `[]` | 合法 |
| 合成"记录里没有关于 X 的内容"这样的条目 | **不做**：等于在 Search 里生成拒答题的答案 |
| 写入时算出、与查询无关的状态标注（"计划，未确认是否发生"） | 倾向可以：它是记忆本身的属性 |
| 读出时针对某个查询临时生成的文字 | 不做 |
| 写"请以新值为准"这类指令 | 不做，以免被当成提示注入 |

### 5.2 以减法为主，标注从严

1. 主手段是选择返回什么：被否认的推断不返回；优先返回编译好的 Line，而不是 100 条原始消息。
2. **被取代的旧值不删、不降成附件**：按 Line 上的顺序给出步骤，标出取代关系和时间。问"现在住哪""2024 年住哪""搬过哪些城市"，用的是同一段带顺序的步骤。
3. 标注只用极少的英文固定短语，每一种单独做消融实验，在拒答题上掉分的就删。
4. 数据源给了消息时间才写消息时间；内容里说到的时间照样保留。

五种效果和底层的对应：

| 效果 | 底层怎么达到 |
|---|---|
| 有证据 | 返回支撑它的步骤，标已发生 |
| 过时 | 步骤链里标出取代关系 |
| 错误 | 拒绝记录拦截，被否认的不返回；用户的纠正本身作为 SB 返回 |
| 无法确认 | 计划没有后续：标"计划，结果未知"；转述、未澄清的矛盾按认知方式标出 |
| 没说过 | 写入侧精炼减少噪声，检索不到就返回 `[]`；不合成"没说过"条目（检索没命中不等于原文里没有，这只能靠写入质量和全局 K 逼近） |

### 5.3 按问题取 Line 上的局部投影

- 查询本身就是唤醒线索。睡着的 Line 和醒着的 Line 平等竞争。
- **交出的是编译好的 Line 局部（命中的 SB 顺着承接取出的、按顺序的关键步骤 + 每步在晨昏线哪一侧），不是互不相连的零散 SB，也不是整条 Line 的全文。** SB 本身就是摘要（§4.4）。
- 按问题取对应的部分：问"葡萄牙玩得怎么样"，读那一片的概括；问"吃得怎么样"，只取吃饭那条；问"为什么去"，取起头那几步。

### 5.4 "没说过"和"无法确认"：实测教训

- 向量余弦、通用重排都分不开"答得上"和"该拒答"：它们判断的是"是不是同一件事"，不是"这个具体事实在不在"。
- 所以不用相关度分数逐题做门槛；返回条数用全局 K，靠端到端测试来定（P1 上 K=20/50/100 成绩接近，K 不是大杠杆）。

### 5.5 双向索引

- 向下（投影 → 原文）：每个投影都能追到支撑它的原文，用于回溯验证。
- 向上（原文 → 投影）：融合检索召回原文后，顺着反向索引找到由它编译出的 SB 和它所在的 Line，一并交给读出。
- 原文命中和 Line 命中是同一份证据的两种表示：双路命中只**提高检索排序**，不算两份独立证据；事实的支撑度按原文来源去重。

### 5.6 计分看回答，不看召回

AML 成绩是平台答题模型读我们的列表后答对与否。R@k（只认原文）只是诊断，不能用来判断 LCE 有没有用。LCE 的预期优势在跨对话、前后变化的关系题（知识更新、事件顺序、时间推理、跨会话推理、偏好演变），要按题型拆开看。

## 7. 评测

| 能力维度 | 本地小测试集题型 | LCE 的作用 |
|---|---|---|
| 记忆治理（更新、遗忘） | knowledge_update | 改了方向仍接原来的步骤，旧计划标为已被取代 |
| 认识论安全 | abstention、LME `_abs` | 精炼读出、全局 K；计划标"未确认" |
| 时间与事件 | temporal_reasoning、event_ordering | Line 上的先后 + 晨昏线时态 |
| 关系与多跳 | contradiction_resolution、multi_session_reasoning | Line 把一件事的多个 SB 串起来 |

- 基线：P1（doubao 向量的融合检索）。参赛门槛：在开放数据集上，LCE 明显胜过 P1。
- 流程：先用小样例看结构对不对（用户审），再逐步扩大；分数下降先分析机制原因，回来讨论，不急着调优；调整只在开发集上做，留出集只验证一次。
- 写入侧指标：断线率（同一推进被拆成几条 Line）、兄弟短线数、不上线的 SB 是否合理、承接是否连对（远处的承接、页内的承接）。
- 编译样例的取材：看用户的判断动作（决定、纠正、反馈），不要用转发的 AI 意见当用户意图。

## 9. 容易犯的错（每一条都犯过）

**结构**

| 错误理解 | 正确理解 |
|---|---|
| Thread 和 Path A 是两个容器，冻结了就把 SB 搬进 Path A | Thread、Path A 是 Line 的两种状态，SB 一直在原处，所在的一侧随时间变 |
| Line 会"结束"，要标 done | Line 永不结束；一步冻结不等于 Line 结束 |
| Line 是单线（贪吃蛇） | 去中心化：分叉、并列、汇合，没有 main |
| 用"分支"理解 Line，默认有主干；分叉时让原来那条保留身份 | 只有 Line；分叉出来的各条地位平等 |
| 预先判断大事小事、主线支线、需求是根，再把点塞进去；或给每步标"服务于谁" | 先有 SB 和承接，Line 是连出来的；子任务关系是长出来之后回头看出来的 |
| 追求一个包罗一切的全貌，混合不同维度的全貌；把维度当成有高低的层级 | 全貌分维度、分阶段，维度是观察角度、没有高低 |
| 编译时先认"这批推进哪件事"，对着摘要挂线，并每窗重写摘要 | 检索直接落在 SB 上；不拿任何概括当吸附内容的容器（实测造成 40 多步直链） |
| 每个 SB 都要上线 | 只按语义和逻辑连，接不上的单独放 |
| Line 有名字，按名字匹配 | 没有名字；内容就在它的 SB 里 |
| 字面上都有"安排"就是同一件事；改了截止日就是新的事 | 反过来：看推进的是不是同一件事；改了方向仍是同一件事 |
| 编译器挂线要经过向量、证据收敛认定 | Path A / Thread 由 LLM 在上下文里显式判断；收敛属于 Path B |
| "LCE" = Path A | LCE 是总称，三部分并列 |
| 重新想买电脑 = 在旧步骤上出新修订 | 事情继续发展：从冻结的旧步骤继续长；只有对过去的认识变了才修订 |
| 树长成时间线是坏事 | 时间是强 alpha 因子；只是别强行按时间接 |
| 自己造概念（"工作集"）、造第二套账本 | 先映射到已有架构；拒绝记录只在 MR-Mem 一处 |
| 原文丢了就把投影藏起来 | 投影保留、标灰、降置信度 |
| 问"这条 Line 整体是 Thread 还是 Path A" | 晨昏线扫过整张图，同一条 Line 上一部分步骤在暗侧、一部分在亮侧 |
| 去界定"一段 Line"从哪到哪；两条 Line 交叉了就要考虑合并 | 不定义线；交叉后可以再分开，只有连续多点重合才是实质重合 |
| 给 SB 再做摘要；读出、检索必须先有 Line 摘要 | SB 本身就是摘要，检索和读出直接落在 SB 上 |

**承接**

| 错误理解 | 正确理解 |
|---|---|
| 代码里留着"没写就接上一块"或"挂到这件事的最新一步"（用户否决过多次，45 步直线就是它造成的） | 没有显式的承接，就不连 |
| 把"对话里接着说的"当成"事情上接着发生的"；把同一时段发生的两件事连起来 | 话头相接、时间重合都不是承接 |
| 把承接理解成因果 | 承接是推进关系；因果写在内容里，取代、矛盾用事实关系字段 |
| 把工作场景的循环当成承接的定义，只连到上一轮的结果 | 循环只是常见情况；承接可以是思想逻辑上接回很久以前的一步 |
| 看到几个节点都出现"错误处理"这类词，就判定该连成线 | 字面相近不等于推进同一件事 |
| 用二元选择（按话题切还是按人切），或把"纵向/横向"固化成数据结构的层级 | 只有 SB 和承接；方向从内容里长出来 |

**SB 粒度**

| 错误理解 | 正确理解 |
|---|---|
| 把 SB 切成原子碎片（问一块、答一块） | SB 跨多个 turn，是避免断章取义的最小完整意思 |
| 一个 SB 装下人的好几次纠偏；一条消息只塞进一个 SB | 每个纠正点各成一个 SB，没编号的也一样 |
| 人和 Agent 的工作对话里，助手的建议单独成一支，节点翻倍 | 只记人的反馈、决定、纠正，以及 Agent 实际做了什么、结果如何 |
| 把"输入→决策→输出"当成一步要装的东西，上一步的结果在下一步再录一遍 | 循环说的是步与步怎么接；上一步的结果用承接指向，不重复录入 |
| 把人的追问、发现问题当成"决策"，或并进一个大的解决问题框架 | 中间一环是反馈或决策；每次反馈也是一步 |
| 从后面几轮读出结果、回写进前一步（只有整库导入才做得到） | 只用当时已知的；Agent 后来的执行和结果是下一个 SB 的前半，承接回前一步 |
| 按"人问一句 + Agent 答一轮"切 SB | 原始需求单独一个 SB；之后每个 SB 是"Agent 提出情况或问题 → 人给出反馈"，看得出遇到了什么、人怎么决定的 |
| 把"人在助手说完后再次开口"当工作场景的断点 | 断点在 SB 收口处：人反馈之后、Agent 下一次汇报之前 |
| 新需求按字面相近挂到原来的 Line 上 | 新需求按语义成新的 SB；有没有承接看后续实际做了什么 |
| "只有最后一步是进行中"理解成全局只能有一个进行中 | 是每条推进路径上没交代结果的末端；并行的几件都可以是进行中 |
| 状态按说话动作标（"在提问"就算进行中） | 状态说的是那件事 |
| Agent 做了很多事就算推进了很多步 | 看有没有推进需求本身 |

**时间**

| 错误理解 | 正确理解 |
|---|---|
| 有时间的计划没发生就一直挂着，或时间一过就当它发生了 | 时间一过冻结的是"当时有过这个计划"，发没发生由后面的步骤说明 |
| 没时间的意图被"下一步"机械扫过；或每次编译都把它塞进候选 | 它休眠，被新内容唤醒时才进候选；可以长出多条 Line；靠编译器读出已定下来才冻结 |
| 给计划加 `time`、`due` 字段 | 那是第三条时间轴；说到的时间写进 SB 内容，比较时读内容 |
| 编造消息时间（用编译时的本机时间） | 数据源没给就只保留先后 |
| 跨多条消息的 SB 只存一个时间点 | 各原文保有自己的时间；SB 的发生时间是区间，`known_at` 是编译时间 |

**提示词与实验**

| 错误理解 | 正确理解 |
|---|---|
| 用一堆条文规则让模型逐条填，出偏差再加规则（补丁循环） | 让模型按原文整体理解；规则越少越好；改之前先上升一层看在修什么，会不会加复杂度和歧义 |
| 把讲解用的比喻当成新概念（纸箱→"Line 是容器"；循环→"一步是闭环"；葡萄牙、电脑、一顿饭写进工作场景的示例；"点"→和"线"对立的模式） | 比喻只帮助理解；落地前映射回已有概念 |
| 同一个东西用多个名字 | 只用 §0.1 的术语 |
| 另起一套话题线、分支、连线的实验提示词，一轮轮补丁，退化成只有点和边的知识图谱，丢了晨昏线、git 式分支 | 回到架构本身，新讲解落在已有结构里 |
| 纠偏时矫枉过正 | 对照用户纠偏和原框架的差异，只改差异的部分 |
| 让 LLM 写编号再由代码补前缀 | 编号只由代码分配 |
| 在 20 条消息的小窗口里逐块编号；按固定条数分页 | 软上限 + 自然断点 + 尾巴带到下一窗 |
| 先切 SB，再拿每个碎片单独判断 | 先整体理解，再切，再连 |
| 用转发的 AI 意见、被误标为用户的系统通知当用户意图 | 取材看用户本人的判断动作 |

## 10. 已定与待定

**已定：**
- 只用双时间轴；计划的时间是内容；没给消息时间就不编造。
- 原文之上全是投影；只有原文不可改，只有系统级人工删除才删；原文丢失时投影标灰不隐藏。
- 推断可回滚，拒绝记录只在 MR-Mem 一处；否认推导和否认结论分开处理。
- 术语以 §0.1 为准；比喻不是概念。
- Line 是事件或思想逻辑的推进过程，由 SB 和承接构成，去中心化，永不结束，没有名字。
- Thread / Path A 是 Line 的两种状态，以晨昏线分界。
- 任何概括都不是吸附内容的容器。
- 承接是推进关系，不是因果，不是话头相接；没写就不连。
- SB 跨多个 turn；一条消息可以分进几个 SB；上一步的结果不重复录入。
- 工作场景：原始需求一个 SB；之后每个 SB 是"Agent 提出情况或问题 → 人给出反馈"；只用当时已知的，不向后读结果；新需求按语义成新 SB，有没有承接看后续实际做了什么（10-16 晚）。
- 自然断点是 SB 完整收口的地方；工作场景在人反馈之后、Agent 下一次汇报之前（10-16 晚）。
- Line 级概括先不做（10-16 晚）。
- 晨昏线扫过整张图，同一条 Line 可以两侧都有步骤。
- 不界定 Line，不管交叉；连续多点重合才是实质重合。
- SB 本身就是摘要；检索候选直接检索 SB。
- 没有时间的意图和计划休眠，被唤醒才进候选。
- 编译窗口：软上限 + 自然断点 + 尾巴带到下一窗；稳定前缀；翻页即压缩。

**待定：**
1. ~~Line 在代码里是什么对象~~：用户 10-16 晚答复，不界定 Line（§4.3）。代码里 `MemoryThread` 和 line 归属怎么清理另议。
2. ~~Line 级缩略描述是否还需要~~：用户 10-16 晚答复，先不做（§4.4）。
3. **没有消息时间的数据，晨昏线以什么为当前**（§2，与外部 v8 冲突）。
4. 合并机制的具体规则：同一节点下挂了几条兄弟短线时，检查一次是否其实是同一推进，要看实际的步骤和证据。两条 Line 交叉不需要合并；连续多点重合才是实质重合。合并是新增一次修订，旧结构保留。
5. 候选每类读多少条，用断线率测定。
