# MR-Mem + LCE 技术报告（AML 2026 第二轮，草稿 2026-10-31）

## 1. 目标和出发点

AML 只比记忆系统本身：平台调用参赛方的 Add 写入对话，再按题调用 Search，拿返回的最多 100 条材料，用平台锁定的模型和提示词答题、评分。所以一个记忆系统能做的全部事情，就是在 Search 时交出一份更好的"笔记"。

我们的基线是 **P1**：把每条消息存为原文单元，用 BM25 和稠密向量两路检索，再用 RRF（k=60，每路 200 个候选）融合排序，直接返回原文。系统里还实现了第三种检索 **HyDE**（Hypothetical Document Embeddings：先让 LLM 针对问题写一段假设的答案，再用它的向量检索），可以作为补救（`fallback`）或常驻的一路（`augmented`）；它每次查询都要多调一次 LLM，所以默认关闭。我们把它接进了 LCE 读出（假设片段与原问题分别检索 SB 和原文，再用 RRF 合并）实测过：在定版配置上，留出集 60 题两遍平均从 58.0 降到 53.1，信息抽取和事件顺序都变差——编译出的 SB 已经覆盖得很好，假设片段带进来的是"像答案但不是原话"的近邻，反而挤掉了真正的证据。所以定版保持关闭，本报告其余结果都在关闭状态下得到。P1 本身就是一个不弱的系统，所以我们给自己定了一个门槛：**不能在开放数据上稳定胜过 P1，就不参赛。**

LCE（Line Chain Evolution）建立在几条原则上：

- **原文是唯一权威，其余都是投影。** 编译出的语义块（SB）、承接、段，都是对原文的理解，可能有错、可以修正；每个投影都要能沿索引回到原文。
- **推理过的不再推理。** 对话发生时已经理解过一遍，编译是顺带留下这次理解。读出时交出编译产物，而不是把大量原文再丢给答题模型重新理解一遍。
- **事情是人推进的。** 助手给出的建议、计划、代码，是人做决定的参考；只有人确认、照做或报告了结果，事情才算发生。
- **只有两条时间轴**：消息时间（源数据给的）和我们发现它的时间。系统导入时间绝不当作事件时间。

## 2. 系统结构

```
原文（每条消息）──BM25 + 稠密向量 + RRF──▶ P1 检索
   │  编译（按窗口，自然断点收口）
   ▼
SB：最小完整意思，带原文起止指针、说话人、状态（已发生/计划/未定）
   │  第二步：承接（after，接着推进）、part（组成部分）、settles（落定）
   ▼
Line：由 SB 和承接组成的树；晨昏线区分进行时（Thread）和过去时（Path A）
   │  分段 + 段摘要（自然断点之后单独调用）
   ▼
段（Thread）：Line 上的一段，一个能单独说"做成/没做成/放弃"的目标；
             摘要＝前因 → 谁 → 何时 → 做了什么 → 后果；记录它从哪一段的哪一步分出
```

**读出（Search）**：

1. 用 P1 的融合检索找到原文命中。
2. 沿反向索引：原文 → 由它编译出的 SB → 沿承接取它所在的 Line 局部。
3. 交出这一片编译产物，以及这些 SB 指向的精确原文片段（不是整条消息）。
4. 可选开关（定版默认关闭，见第 4 节）：按段内顺序展开（`carry=threads`）；**融合**，即再从 P1 的命中里按名次补原文，但只补"没有任何已给出的 SB 引用过"的记录（`raw_fill`）。

## 3. 开发过程：瓶颈、弯路和解决

### 3.1 助手说的话被当成了事实（语义权威）

**现象**：拒答题大量失分。例如问"6 月 14 日和 HR 的电话谈了什么"（原文里根本没谈），系统答出了一串福利条目——那是助手为这通电话准备的话术。

**原因**：编译规则把"助手陈述的事实和解释"标为已发生、已确认；读出时助手的 SB 占了多数，答题模型把计划当成了经过。

**解决**：
- 助手的 SB 只写"它给了什么、为人的哪件事给的"，不列具体内容（具体内容留在原文，靠索引取）。
- 读出时助手的 SB 只取第一行，挂在它所回应的那个人的步骤下面，标"Agent told the person"。
- 只有人报告了结果才算"落定"；人再问一次、或者只是助手这么说，都不算。

**效果**：那道题在所有配置下都答对；拒答从 25 回到 50–75；事件顺序题从个位数升到 20–37——助手不再列计划清单后，答题模型改按人实际推进的顺序回答。

### 3.2 时间：没有消息时间的数据

**现象**：BEAM 每段会话只有第一条消息带时间。新旧值都在读出里（测试覆盖率 65% 和后来的 78%），答题模型挑了旧值；"测验成绩提高"那一步看不到日期，算日期差只能答 0 天。

**弯路**：最早没给时间的消息被填成了导入时间。后来改成不显示时间，又丢掉了先后。

**解决**：没有时间的消息，取同一会话里、在它之前最近一条有源时间的消息，标成"会话始于 MM-DD"（不往后借、不跨会话借、绝不用导入时间）；编译时另给位置编号（`S1 #45`）表示真实顺序。

**效果**：知识更新题 66.7 → 83.3，两遍一致。

### 3.3 局部投影答不了全局题

**现象**：总结题、"按顺序列出我提过的方面"这类题，按问题取的局部只覆盖历史的一小块。

**弯路一**：把每件事开头那一句拼成提纲——有 204 行、3.4 万字符，比 P1 给的还多，还带着旧值，总分没升。原因是结构里缺了"事"这一层：线太粗（每段历史只有几条线，最大一条近 700 步），步太细。

**弯路二**：恢复"段"（Thread）时，摘要先限成"两句话"，丢了过程；接着写成了逐步流水账（一段塞进 183 个 SB，每段几千字）；又反复改"段"的定义，在太细和太粗之间来回摆。

**转折**：同一段 44 个 SB，单独用一句朴素要求"用几句话总结：为了什么、谁做了什么、最后怎样"，两个模型都写出了 900 字左右的真正总结。问题不在模型，在流程：摘要塞在连线那次调用里，每窗只看到这一窗，就一直往后追加；而规定"每行填满五个要素"等于让模型逐条填空。

**解决**：分段和总结在自然断点之后单独调用。分段时对照具体的候选步骤（每步标着所属段）判断归属，不只看摘要；总结用朴素要求，旧摘要 + 本窗新 SB 重写。

**效果**：同一份编译上，按段承接比原来的局部读出高 9 分（20 题），总结题接近满分。每窗多两次短调用，输入 token 只多约 1%。

### 3.4 把分段塞进连线，连线变差

**现象**：让第二步一次同时连线和分段，同一套读出在同 20 题上从约 63 掉到约 54。

**排查**：把分段拆成单独调用后，连线仍没恢复——真正的差别在第二步看到的时间：修掉导入时间后，同一会话的步骤全是同一个日期，模型失去了先后。改为给位置编号。同一段历史四次编译的分数在 54–63 之间，编译本身的波动也不小。

### 3.5 和 P1 的融合

**弯路**：直接把 P1 的前 20 条原文拼在 LCE 读出后面，得分反而更低（拒答掉到 25）。原因是同一份证据给了两遍：LCE 给的是精确片段，P1 给的是整条原文，按文本去重去不掉。

**解决**：按原文记录去重，P1 只补"没有任何已给出的 SB 引用过"的原文。LCE 给结构和精确片段，P1 补编译没覆盖到的证据，两边分工。

**效果**：同样的字符预算下比 P1 高 7–9 分，拒答也从 50 升到 66.7。

### 3.6 工程

- **JSON 解析**：模型把代码里的双引号原样抄进字符串，整份输出作废；重试三次输出一样。改为解析失败时只修补单行字段里没转义的引号。
- **续编冲突**：一段历史先结束时会编译所有用户的剩余窗口，和另一段历史的线程同时编同一个窗口，写入了同一 ID 的两份内容。改为只编自己用户的窗口、持用户锁，窗口应用以日志里第一份为准。
- **只改读出的快速循环**：编译结果可重放，读出改动不调模型，一轮从约 70 分钟降到 4–5 分钟。
- **答题噪声**：同一份读出答两遍就能差 3 分。所有比较每组答两遍取平均，单次 3 分以内的差不下结论；改动是否起效，看它针对的题有没有按机制答对。
- **服务契约**：编译失败只保留原文、照样返回 200；平台不调 flush，所以每个用户第一次 Search 时先编完剩下的尾巴窗口。

### 3.7 评测方法上的纠偏

- 一度在"LCE 单独全面超过 P1"上硬磨。后来改为：LCE 是 P1 的补充，比较"P1 + LCE"对 P1，按题型看，并报告每题交给答题模型的字符数。
- 开发集只有 40 题（每类 4 题）时，很多结论在换题后不成立（例如"P1 擅长细节题"）。于是改用从未用过的 BEAM 100K 留出集（60 题）验证；但之后的诊断和配置选择也反复用了这 60 题，所以它已不再是独立的留出集。第 4 节的留出集分数应看作"开发中的验证"，独立验证要在没有参与调整的数据上另做（见第 5 节）。

## 4. 结果

答题模型：DeepSeek（本地模拟平台答题，提示词与官方一致）；每组答两遍取平均。

**BEAM 100K 留出集（3 段历史，60 题）**

| 配置 | 平均 | 每题字符 |
|---|---|---|
| P1（原文融合检索） | 47.2 | 4.8 万 |
| LCE 局部读出（只给编译产物 + 精确片段） | 51.6 | 2.1 万 |
| LCE + 融合（v11 编译） | **56.3** | 4.8 万 |
| LCE 按段承接 + 融合（v13 编译） | **54.2** | 5.0 万 |
| **最终配置（v14 编译 + 局部读出）** | **58.0** | 2.0 万 |
| v14 + 按段承接 | 53.6 | 2.4 万 |
| v14 + 融合 | 52.4 | 4.9 万 |

- 最终配置比 P1 高 10.8 分，交给答题模型的材料只有 P1 的 42%。
- 段承接和融合的作用取决于连线质量：在连线较差的编译（v11、v13）上，它们能补回 3–5 分；在连线好的定版编译上，按承接取局部就够了，补 20 条原文反而降分。
- **但只用局部读出，就把 P1 的证据丢了。** mini 套件的 CLBench-life（25 题）上，LCE 局部读出 0 分、P1 8.3 分：题目要对用户贴进来的整份材料（如 11 万字符的锻炼记录表）做统计，编译产物把表压成了一句"用户贴了一段记录"，读出给不出具体行。LCE 应当是"P1 + 结构"，不能低于 P1：有些题纯原文检索就够了。所以定版改为默认打开兜底（`raw_fill: 100`）：LCE 的线和精确片段在前，后面按 P1 的检索顺序补满到平台的 top_k=100，已被 SB 引用的原文不重复给。这一改动在 BEAM 上会不会降分、在 CLBench 上能补回多少，**尚未实测**（火山额度用完）。
- 提升集中在事件顺序（约 7 → 30+）、知识更新、偏好、总结、拒答。
- 矛盾题两边都接近 0：前后矛盾的两种说法都在材料里，答题模型（官方提示词要求"只输出答案"）只答一边。

**PersonaMem-v2 32K（2 段，33 题）**：P1 56.1，LCE 57.6，打平。这类题的答案多在单句陈述里，结构优势用不上。

**成本（定版 v14 编译，BEAM 100K 留出集，约 140 万字符历史）**：136 次调用（含分段、段摘要两步），输入约 175 万 token、输出约 29 万 token；三段并行约 61 分钟。

## 5. 局限

- **独立验证还缺**：第 4 节 BEAM 留出集的 60 题在开发中被反复使用；mini 套件（AML 公开数据的抽样）只跑了一部分，且大多数据集只编了开头一段就因额度停止。
- 编译结果有波动：同一段历史多次编译，读出分数相差可达 9 分。
- 编译场景只做了"人和助手"，人与人的聊天按同一方式编，效果未验证。
- 矛盾类题没有专门处理（我们选择不把"冲突"做成编译产物，留给答题方判断）。
- 所有增益在豆包 seed 2.1 pro 编译、doubao-embedding-vision 向量下测得；换模型需重新验证。平台的答题模型比本地用的弱时效果如何，未测。
