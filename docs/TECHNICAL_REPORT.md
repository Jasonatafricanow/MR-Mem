# MR-Mem + LCE 技术报告（AML 2026 第二轮，草稿 2026-10-31）

## 1. 目标和出发点

AML 只比记忆系统本身：平台调用参赛方的 Add 写入对话，再按题调用 Search，拿返回的最多 100 条材料，用平台锁定的模型和提示词答题、评分。所以一个记忆系统能做的全部事情，就是在 Search 时交出一份更好的"笔记"。

我们的基线是 **P1**：把每条消息存为原文单元，用 BM25 和稠密向量两路检索，再用 RRF（k=60，每路 200 个候选）融合排序，直接返回原文。系统里还实现了第三种检索 **HyDE**（Hypothetical Document Embeddings：先让 LLM 针对问题写一段假设的答案，再用它的向量检索），可以作为补救（`fallback`）或常驻的一路（`augmented`）；它每次查询都要多调一次 LLM，所以默认关闭。我们把它接进了 LCE 读出（假设片段与原问题分别检索 SB 和原文，再用 RRF 合并）实测过：在 v14 配置上，留出集 60 题两遍平均从 58.0 降到 53.1，信息抽取和事件顺序都变差——编译出的 SB 已经覆盖得很好，假设片段带进来的是"像答案但不是原话"的近邻，反而挤掉了真正的证据。所以定版保持关闭，本报告其余结果都在关闭状态下得到。P1 本身就是一个不弱的系统，所以我们给自己定了一个门槛：**不能在开放数据上稳定胜过 P1，就不参赛。**

LCE（Line Chain Evolution）建立在几条原则上（定义见 `docs/LCE_FROZEN.md`）：

- **原文是唯一权威，其余都是投影。** 编译出的语义块（SB）、Line、段，都是对原文的理解，可能有错、可以修正；每个投影都要能沿索引回到原文。
- **推理过的不再推理。** 对话发生时已经理解过一遍，编译是顺带留下这次理解。读出时交出编译产物，而不是把大量原文再丢给答题模型重新理解一遍。
- **事情是人推进的。** 助手给出的建议、计划、代码，是人做决定的参考；只有人确认、照做或报告了结果，事情才算发生。
- **只有两条时间轴，而且都是消息的时间**：消息什么时候说的（源数据给的时间戳）、系统什么时候拿到它。内容里说到的时间是内容；系统导入时间绝不当作事件时间。

## 2. 系统结构

```
原文（每条消息）──BM25 + 稠密向量 + RRF──▶ P1 检索
   │  编译（按窗口，自然断点收口；每窗 2 次调用）
   ▼
SB：在聊的那件事（主语 + 谓语 + 宾语：谁、做了什么、哪件事），可跨上百轮；
    具体内容（数字、步骤、代码、时间）不抄进 SB，留在原文，靠索引取
   │  第 2 次调用：把这一窗的 SB 切成段，给已经收口的段写一次摘要
   ▼
Line：由 SB 和承接组成，一直在长；晨昏线区分还在进行的（Thread）和已经冻结的（Path A）
段：Line 上已经长成的一截；摘要＝前因 → 谁 → 何时 → 做了什么 → 后果，写一次就定下，
    不写具体数值，除非数值本身就是结果
```

**读出（Search）**：

1. 用 P1 的融合检索找到原文命中（前 30 条）。
2. 沿反向索引：每条原文命中 → 由它编译出的 SB（`hit_anchors`：不受 SB 数上限截断）→ SB 在 Line 上的近邻（relay）。SB 下只挂检索命中的原文（`raw_of_sb: hits`），每条原文带消息时间。
3. 全部段摘要（`thread_k: 60`），以及人的长期指令和偏好。
4. 晨昏线的标记（已发生 / 进行中 / 后来落定）是记忆侧自己的判断，不给答题模型看（`marks: false`）。
5. 不按 P1 补位（`raw_fill: 0`）：原文 → SB → Line、段摘要 → SB → 原文两条路，证据已经够。
6. **决策模型旁路**（`decision`）：百炼 `decision-model-preview`，在 Search 时对问题和它的原文命中做判断，必要时在读出最前面加一条说明（见 3.11）。它只判断、不改证据，也不写进编译产物。

## 3. 开发过程：瓶颈、弯路和解决

3.1–3.7 是 v14 及之前的过程，3.8 起是 10-31 换成定版流程的过程。

### 3.1 助手说的话被当成了事实（语义权威）

**现象**：拒答题大量失分。例如问"6 月 14 日和 HR 的电话谈了什么"（原文里根本没谈），系统答出了一串福利条目——那是助手为这通电话准备的话术。

**原因**：编译规则把"助手陈述的事实和解释"标为已发生、已确认；读出时助手的 SB 占了多数，答题模型把计划当成了经过。

**解决**：
- 助手的 SB 只写"它给了什么、为人的哪件事给的"，不列具体内容（具体内容留在原文，靠索引取）。
- 读出时助手的 SB 只取第一行，挂在它所回应的那个人的步骤下面，标"Agent told the person"。
- 只有人报告了结果才算"落定"；人再问一次、或者只是助手这么说，都不算。

**效果**：那道题在所有配置下都答对；拒答从 25 回到 50–75；事件顺序题从个位数升到 20–37——助手不再列计划清单后，答题模型改按人实际推进的顺序回答。

### 3.2 时间：没有消息时间的数据

**现象**：BEAM 每段会话只有第一条消息带时间。新旧值都在读出里（测试覆盖率 65% 和后来的 78%），答题模型挑了旧值；"测验成绩提高"那一步看不到日期，算日期差只能答 0 天。

**弯路**：最早没给时间的消息被填成了导入时间。后来改成不显示时间，又丢掉了先后。

**解决**：没有时间的消息，取同一会话里、在它之前最近一条有源时间的消息，标成"会话始于 MM-DD"（不往后借、不跨会话借、绝不用导入时间）；编译时另给位置编号（`S1 #45`）表示真实顺序。

**效果**：知识更新题 66.7 → 83.3，两遍一致。

### 3.3 局部投影答不了全局题

**现象**：总结题、"按顺序列出我提过的方面"这类题，按问题取的局部只覆盖历史的一小块。

**弯路一**：把每件事开头那一句拼成提纲——有 204 行、3.4 万字符，比 P1 给的还多，还带着旧值，总分没升。原因是结构里缺了"事"这一层：线太粗（每段历史只有几条线，最大一条近 700 步），步太细。

**弯路二**：恢复"段"时，摘要先限成"两句话"，丢了过程；接着写成了逐步流水账（一段塞进 183 个 SB，每段几千字）；又反复改"段"的定义，在太细和太粗之间来回摆。

**转折**：同一段 44 个 SB，单独用一句朴素要求"用几句话总结：为了什么、谁做了什么、最后怎样"，两个模型都写出了 900 字左右的真正总结。问题不在模型，在流程：摘要塞在连线那次调用里，每窗只看到这一窗，就一直往后追加；而规定"每行填满五个要素"等于让模型逐条填空。

**解决**：分段和总结在自然断点之后单独调用。

**效果**：同一份编译上，按段承接比原来的局部读出高 9 分（20 题），总结题接近满分。

### 3.4 把分段塞进连线，连线变差

**现象**：让第二步一次同时连线和分段，同一套读出在同 20 题上从约 63 掉到约 54。

**排查**：把分段拆成单独调用后，连线仍没恢复——真正的差别在第二步看到的时间：修掉导入时间后，同一会话的步骤全是同一个日期，模型失去了先后。改为给位置编号。同一段历史四次编译的分数在 54–63 之间，编译本身的波动也不小。

### 3.5 和 P1 的融合

**弯路**：直接把 P1 的前 20 条原文拼在 LCE 读出后面，得分反而更低（拒答掉到 25）。原因是同一份证据给了两遍：LCE 给的是精确片段，P1 给的是整条原文，按文本去重去不掉。

**解决**：按原文记录去重，P1 只补"没有任何已给出的 SB 引用过"的原文。后来定版去掉了补位（见 3.9）。

### 3.6 工程（v14 时期）

- **JSON 解析**：模型把代码里的双引号原样抄进字符串，整份输出作废；重试三次输出一样。改为解析失败时只修补单行字段里没转义的引号。
- **续编冲突**：一段历史先结束时会编译所有用户的剩余窗口，和另一段历史的线程同时编同一个窗口，写入了同一 ID 的两份内容。改为只编自己用户的窗口、持用户锁，窗口应用以日志里第一份为准。
- **只改读出的快速循环**：编译结果可重放，读出改动不调模型，一轮从约 70 分钟降到 4–5 分钟。
- **服务契约**：编译失败只保留原文、照样返回 200；平台不调 flush，所以每个用户第一次 Search 时先编完剩下的尾巴窗口。

### 3.7 评测方法上的纠偏

- 一度在"LCE 单独全面超过 P1"上硬磨。后来改为：LCE 是 P1 的补充，按题型看，并报告每题交给答题模型的字符数。
- 开发集只有 40 题（每类 4 题）时，很多结论在换题后不成立。于是改用从未用过的 BEAM 100K 留出集（60 题）验证；但之后的诊断和配置选择也反复用了这 60 题，所以它已不再是独立的留出集。第 4 节的留出集分数应看作"开发中的验证"。
- **答题噪声**：同一份读出答两遍能差 3 分，30–40 题的集上两遍之间最多差 9 分。所有比较每组答两遍取平均；改动是否起效，看它针对的题有没有按机制答对。
- **改哪层只重跑哪层**：只改读出就只重跑读出；只改段层就复制原始记录和 SB、清掉段，再续编（一次 80 秒、34 次调用）；只有改了第一步才整套重编。否则 SB 那一步每次输出的随机差异会混进比较里。

### 3.8 编译层回到冻结的定义

**现象**：换上 mini 套件（AML 公开数据抽样）后，v14 编译暴露出切得过细：LoCoMo（人与人的短句聊天）一条消息一个 SB，打招呼也算，一窗 341 条消息撞上 1.6 万 token 的输出上限，两个窗口全部失败；PersonaMem v1 里人讲一段自己的感受，被逐句切成几十个 SB；人贴进来的文档、群聊导出被逐行当成人的话。60 题的编译要近半小时（1755 秒）。

**原因**：我们在实现里反复改动 SB、段、Line 的层级（SB 被当成"一个点"，段被当成"一件事"），每次压缩上下文后又打一个补丁。

**解决**：把已经说清楚的定义冻结成 `docs/LCE_FROZEN.md`，实现、提示词、读出都照它来：
- SB 是在聊的那件事，一百轮也是一个 SB；用句子主干（谁 + 做了什么 + 哪件事）写理解，不抄具体内容和时间。
- 段摘要写一次、写已经成熟的那一截，结构是前因-谁-何时-做了什么-后果；单独的承接层是多余的，从哪来、引出了什么写在前因和后果里。
- 每窗 2 次调用：SB 一次，段一次。

**效果**（BEAM 100K 留出集 60 题，同一份缓存向量，两遍）：新流程 49.9，v14 + 补位 50.2，打平；编译从 1755 秒降到 237 秒，68 次调用、66 万输入 + 4 万输出 token。LoCoMo 小样本 61.7 对 P1 48.4。

### 3.9 读出：复用 relay，不重新造

- **只挂命中的原文**：SB 变成一件事之后可以跨很多条消息，relay 把一个 SB 的全部来源原文倒出来，LoCoMo 上只有 36.7；改为只挂检索命中的原文，61.7。
- **不补位**（用户定）：证据有两条路就够了，补位的边际收益低，分差在答题波动之内。每题字符降到 P1 的一半左右。
- **全部段摘要**：原来只按相似度给 3 段，而总结、计数类题问的是全局；给全部段摘要后总结题 57 → 75，总分 49.4 → 50.3。
- **晨昏线标记不给答题模型**：长期偏好段还漏着 `[confirmed; before]`，已去掉。
- **SB 数上限截断了原文命中**：读出按"原文命中 + SB 检索"合并排序后只取前 16 个 SB 当锚点，原文命中的 SB 排在 16 名外就连同原文一起丢了——60 题的前 30 条原文命中里丢了 208 条，人的消息 128 条，前 10 名里 12 条。一道时间题的答案原文（"API key obtained on March 10"）在原文检索里排第 3，就这样没了。这个上限是 10-29 在旧编译上定的，换了 SB 粒度和补位方式后没有重查。改为每条原文命中都带出它的 SB（`hit_anchors`）：时间推理两遍都 33 → 50，总分 58.5 → 60.1。

### 3.10 时间转换和读出用了两套标准

**现象**：读出里写"会话开始于 03-14"，人自己却说"3 月 15 日开会"。

**原因**：本地评测数据的转换脚本用 `datetime.strptime(...).timestamp()`，按转换机器的本地时区解析；运行时按 UTC 显示。BEAM 100K 和 LoCoMo 是在 UTC+8 的机器上转的，所有日期早了一天；BEAM 500K/1M 和 LongMemEval 是在固定 UTC−7 的机器上转的（LME 用题目里原样保留的提问时间交叉验证：提问早于会话的违例从 23 条降到 5 条）。

**解决**：转换统一按 UTC 解析；本地数据全部改正；已编译的库改时间、重算请求哈希，只重跑段层（段摘要里写的日期也跟着改正）。

### 3.11 决策模型旁路

**起点**：矛盾题两边都接近 0——人既说过做了、又说过"从没做过"，两句都在读出里，答题模型只看到一边就答"No"。拒答题则是答题模型把助手的建议当成了人做过的事：问"我执行了哪些 ESLint 规则"，规则清单是助手给的示例，人从没说过。两类都需要在检索之后"理解"一次，而我们不把冲突做成编译产物。

**做法**：Search 时用百炼的决策模型（System One，输出是/否的概率或选择）做旁路，规则在答题前定死：
- 先分流：这题是"问人有没有做过某事"、"问人自己的某个具体信息"，还是其他（60 题里，选成前者的正好是 6 道矛盾题）。
- **矛盾**：对"有没有做过"的题，逐条判断前 30 条原文命中里人的消息是说做过还是说从没做过；两边都有（概率 ≥ 0.5）就在读出最前面引用两句原话。只判断人的消息：决策模型会把助手的话当成人说的。
- **没说过**：对"具体信息"的题，整组判断这个信息是人说过的、只在助手的建议里，还是根本没有；后两种就说明一句。
- 调用在服务的主线程外并行，失败就不加说明。

**效果**（只重答挂上说明的 18 题，其余沿用）：52.6 → 58.5；矛盾 8 → 50，拒答 50 → 67。

**试过、没用、放弃的**：
- 逐条给 P1 的候选打相关度再重排：留出集 +2.4，换到 mini 套件 −4.2；知识更新被拉低（新旧值都"相关"）。
- 拒答用"人自己有没有给出这个信息"逐条判断、或整组判断"只凭人说的话能不能答"：分不开拒答题和其它题。
- 矛盾说明再加一句"这些消息没有说哪个是定论"：不变，官方提示词要求只输出答案，模型不会反问。
- 多会话：让决策模型挑出相关原文按时间列清单——路由太宽（36/60），挑中的多是带代码的长消息，多会话 33 → 19。

### 3.12 工程（定版流程）

- **主线程瓶颈**：编译的模型调用原来在服务的主线程上串行，改成生成器协议，存储操作留在主线程、模型调用在外面并行。pm2_32k 编译 1173 秒 → 199 秒。
- **向量不确定**：同一文本两次请求返回的向量不完全一样（余弦约 0.998），跨次比较时读出会抖。加了本地向量缓存（SQLite，按模型、维度、文本哈希），重启重建索引不重复付费，比较也确定了。
- **覆盖检查误判**：模型按规则在停点停下、遇到贴进来的规则书只给提问立 SB、遇到机器日志给空数组，都被"覆盖不到一半"判成坏答案重试三次。改为看停点前最后一条消息有没有覆盖、空数组直接接受。15 份存下来的失败答案回放全部通过。
- **评分截断**：CLBench 的评分理由写到 4000 token 被截断，没写到分数。评分改用单独的 12000 token 后端。

## 4. 结果

答题模型：deepseek-v4.1-flash（本地模拟平台答题，提示词与官方一致）；每组答两遍取平均。编译模型：deepseek-v4.1-flash-1017（Token Plan）；向量：qwen3.7-text-embedding-flash（带缓存）。

| 配置 | 两遍 | 平均 | 每题字符 |
|---|---|---|---|
| P1（原文融合检索） | 47.3 / 47.0 | 47.2 | 4.8 万 |
| v14 编译 + 补位 | | 50.2 | |
| 新流程，全部段摘要，不补位 | 51.4 / 49.2 | 50.3 | 8.5 万 |

- 定版比 P1 高 12.9 分。
- 时间转换修正那一行同时重跑了段层，段层输出本身有随机性（总结题 75 → 51、多会话 20 → 37.5），这 2.3 分不能全算到日期上。

| deepseek-v4.1-flash | 51.9 | 48.5 |
| qwen3.8-flash | 47.6 | 41.4 |

两个模型都是 LCE 领先。平台默认的答题模型（Qwen3-14B）本地没有可用的接口，未测。

**答题侧的失分**：有标准证据的 36 题逐条核对，失败题的证据大多在读出里。很多失分来自官方 BEAM 答题提示词的两条要求——"只用上下文、不要用自身知识"和"直接简洁、只输出答案、不要解释"：时间题只写天数、没写起止日期，只得一半分；人说过"讲概率时总要分步讲解"，模型照提示词不解释；问"红牌概率怎么算"，模型答"上下文里没有"。这对所有记忆系统一样。

**其它数据集**（v14 时期，mini 套件，两遍）：pm2_32k P1 54.6 → LCE 62.1；pm1_32k 81.7 → 86.7；LoCoMo（人与人模板）50.0 → 63.3；CLBench 两边都只对一两题（评分细则全对才得分），打平。定版流程在这些数据集上还没有整套重测。

**成本（定版流程，BEAM 100K 留出集，约 140 万字符历史）**：68 次调用，输入约 66 万 token、输出约 4 万 token，三段并行约 4 分钟。决策旁路每次 Search 1 次分流调用，"有没有做过"类再加至多 30 次，"具体信息"类再加 1 次。

## 5. 局限

- **独立验证还缺**：BEAM 留出集的 60 题在开发中被反复使用；定版流程和决策旁路都没有在别的数据集上整套验证。
- **段层输出不稳定**：编译温度为 0，同一份 SB 上重跑段层（那次同时改正了日期），总结题从 75 变到 51。
- **多会话、事件顺序没有解决**：多会话的失分是跨多处计数、比较时答错，以及计数口径模糊；事件顺序的先后都对，丢分在"挑哪几件"（标准答案每个阶段挑一件，模型从头开始挑）。记忆侧试过的办法都没有用。
- 决策模型是预览版（`decision-model-preview`），正式评测期间是否可用、限流如何，不由我们控制；不可用时服务照常，只是不加说明。
- 平台的答题模型比本地用的弱时效果如何，未测。
