# MR-Mem + LCE 技术报告（AML 2026 第二轮，2026-10-31 草稿，11-02 补正式评测复盘）

## 1. 目标和出发点

AML 只比记忆系统本身：平台调用参赛方的 Add 写入对话，再按题调用 Search，拿返回的最多 100 条材料，用平台锁定的模型和提示词答题、评分。所以一个记忆系统能做的全部事情，就是在 Search 时交出一份更好的"笔记"。

我们的基线是 **P1**：把每条消息存为原文单元，用 BM25 和稠密向量两路检索，再用 RRF（k=60，每路 200 个候选）融合排序，直接返回原文。系统里还实现了第三种检索 **HyDE**（Hypothetical Document Embeddings：先让 LLM 针对问题写一段假设的答案，再用它的向量检索），可以作为补救（`fallback`）或常驻的一路（`augmented`）；它每次查询都要多调一次 LLM，所以默认关闭。我们把它接进了 LCE 读出（假设片段与原问题分别检索 SB 和原文，再用 RRF 合并）实测过：在 v14 配置上，留出集 60 题两遍平均从 58.0 降到 53.1，信息抽取和事件顺序都变差——编译出的 SB 已经覆盖得很好，假设片段带进来的是"像答案但不是原话"的近邻，反而挤掉了真正的证据。所以定版保持关闭，本报告其余结果都在关闭状态下得到。P1 本身就是一个不弱的系统，所以我们给自己定了一个门槛：**不能在开放数据上稳定胜过 P1，就不参赛。**

LCE（Line Chain Evolution）建立在几条原则上（定义见 `docs/LCE_FROZEN.md`）：

- **原文是唯一权威，其余都是投影。** 编译出的语义块（SB）、Line、段，都是对原文的理解，可能有错、可以修正；每个投影都要能沿索引回到原文。
- **推理过的不再推理。** 对话发生时已经理解过一遍，编译是顺带留下这次理解。读出时交出编译产物，而不是把大量原文再丢给答题模型重新理解一遍。
- **事情是人推进的。** 助手给出的建议、计划、代码，是人做决定的参考；只有人确认、照做或报告了结果，事情才算发生。
- **只有两条时间轴，而且都是消息的时间**：消息什么时候说的（源数据给的时间戳）、系统什么时候拿到它。内容里说到的时间是内容；系统导入时间绝不当作事件时间。

## 2. 系统结构

```
原文（每条消息）──BM25 + 稠密向量 + RRF──▶ P1 检索
   │  编译（按窗口，自然断点收口；每窗 2 次调用）
   ▼
SB：在聊的那件事（主语 + 谓语 + 宾语：谁、做了什么、哪件事），可跨上百轮；
    具体内容（数字、步骤、代码、时间）不抄进 SB，留在原文，靠索引取
   │  第 2 次调用：上一窗没收口那一段的 SB 放在序列开头，和这一窗的 SB 一起切成段，
   │  给已经收口的段写一次摘要
   ▼
Line：由 SB 和承接组成，一直在长；晨昏线区分还在进行的（Thread）和已经冻结的（Path A）
段：Line 上已经长成的一截；摘要＝前因 → 谁 → 何时 → 做了什么 → 后果，写一次就定下，
    不写具体数值，除非数值本身就是结果
```

**读出（Search）**：

1. 用 P1 的融合检索找到原文命中（前 30 条）。
2. 沿反向索引：每条原文命中 → 由它编译出的 SB（`hit_anchors`：不受 SB 数上限截断）→ SB 在 Line 上的近邻（relay）。SB 下只挂检索命中的原文（`raw_of_sb: hits`），每条原文带消息时间。
3. 全部段摘要（`thread_k: 60`），每条带它首尾一步的位置和时间（`thread_span`）；人的长期指令和偏好，其中遗忘请求单独列出，标明每条只管它说的那一件（`forget_scope`）。
4. 晨昏线的标记（已发生 / 进行中 / 后来落定）是记忆侧自己的判断，不给答题模型看（`marks: false`）。
5. 不按 P1 补位（`raw_fill: 0`）：原文 → SB → Line、段摘要 → SB → 原文两条路，证据已经够。命中的原文整条给出。条数超过 top_k 时，先去掉离问题最远的段摘要，原文命中不动。
6. **决策模型旁路**（`decision`）：`decision-model-preview`（走 Token Plan），在 Search 时判断问题和读出自己的原文命中，人自己的命中消息里既说做过、又说从没做过时，在读出最前面引用这两句原话（见 3.11）。它只判断、不改证据，也不写进编译产物。

## 3. 开发过程：瓶颈、弯路和解决

3.1–3.7 是 v14 及之前的过程，3.8 起是 10-31 换成定版流程的过程。

### 3.1 助手说的话被当成了事实（语义权威）

**现象**：拒答题大量失分。例如问"6 月 14 日和 HR 的电话谈了什么"（原文里根本没谈），系统答出了一串福利条目——那是助手为这通电话准备的话术。

**原因**：编译规则把"助手陈述的事实和解释"标为已发生、已确认；读出时助手的 SB 占了多数，答题模型把计划当成了经过。

**解决**：
- 助手的 SB 只写"它给了什么、为人的哪件事给的"，不列具体内容（具体内容留在原文，靠索引取）。
- 读出时助手的 SB 只取第一行，挂在它所回应的那个人的步骤下面，标"Agent told the person"。
- 只有人报告了结果才算"落定"；人再问一次、或者只是助手这么说，都不算。

**效果**：那道题在所有配置下都答对；拒答从 25 回到 50–75；事件顺序题从个位数升到 20–37——助手不再列计划清单后，答题模型改按人实际推进的顺序回答。

### 3.2 时间：没有消息时间的数据

**现象**：BEAM 每段会话只有第一条消息带时间。新旧值都在读出里（测试覆盖率 65% 和后来的 78%），答题模型挑了旧值；"测验成绩提高"那一步看不到日期，算日期差只能答 0 天。

**弯路**：最早没给时间的消息被填成了导入时间。后来改成不显示时间，又丢掉了先后。

**解决**：没有时间的消息，取同一会话里、在它之前最近一条有源时间的消息，标成"会话始于 MM-DD"（不往后借、不跨会话借、绝不用导入时间）；编译时另给位置编号（`S1 #45`）表示真实顺序。

**效果**：知识更新题 66.7 → 83.3，两遍一致。

### 3.3 局部投影答不了全局题

**现象**：总结题、"按顺序列出我提过的方面"这类题，按问题取的局部只覆盖历史的一小块。

**弯路一**：把每件事开头那一句拼成提纲——有 204 行、3.4 万字符，比 P1 给的还多，还带着旧值，总分没升。原因是结构里缺了"事"这一层：线太粗（每段历史只有几条线，最大一条近 700 步），步太细。

**弯路二**：恢复"段"时，摘要先限成"两句话"，丢了过程；接着写成了逐步流水账（一段塞进 183 个 SB，每段几千字）；又反复改"段"的定义，在太细和太粗之间来回摆。

**转折**：同一段 44 个 SB，单独用一句朴素要求"用几句话总结：为了什么、谁做了什么、最后怎样"，两个模型都写出了 900 字左右的真正总结。问题不在模型，在流程：摘要塞在连线那次调用里，每窗只看到这一窗，就一直往后追加；而规定"每行填满五个要素"等于让模型逐条填空。

**解决**：分段和总结在自然断点之后单独调用。

**效果**：同一份编译上，按段承接比原来的局部读出高 9 分（20 题），总结题接近满分。

### 3.4 把分段塞进连线，连线变差

**现象**：让第二步一次同时连线和分段，同一套读出在同 20 题上从约 63 掉到约 54。

**排查**：把分段拆成单独调用后，连线仍没恢复——真正的差别在第二步看到的时间：修掉导入时间后，同一会话的步骤全是同一个日期，模型失去了先后。改为给位置编号。同一段历史四次编译的分数在 54–63 之间，编译本身的波动也不小。

### 3.5 和 P1 的融合

**弯路**：直接把 P1 的前 20 条原文拼在 LCE 读出后面，得分反而更低（拒答掉到 25）。原因是同一份证据给了两遍：LCE 给的是精确片段，P1 给的是整条原文，按文本去重去不掉。

**解决**：按原文记录去重，P1 只补"没有任何已给出的 SB 引用过"的原文。后来定版去掉了补位（见 3.9）。

### 3.6 工程（v14 时期）

- **JSON 解析**：模型把代码里的双引号原样抄进字符串，整份输出作废；重试三次输出一样。改为解析失败时只修补单行字段里没转义的引号。
- **续编冲突**：一段历史先结束时会编译所有用户的剩余窗口，和另一段历史的线程同时编同一个窗口，写入了同一 ID 的两份内容。改为只编自己用户的窗口、持用户锁，窗口应用以日志里第一份为准。
- **只改读出的快速循环**：编译结果可重放，读出改动不调模型，一轮从约 70 分钟降到 4–5 分钟。
- **服务契约**：编译失败只保留原文、照样返回 200；平台不调 flush，所以每个用户第一次 Search 时先编完剩下的尾巴窗口。

### 3.7 评测方法上的纠偏

- 一度在"LCE 单独全面超过 P1"上硬磨。后来改为：LCE 是 P1 的补充，按题型看，并报告每题交给答题模型的字符数。
- 开发集只有 40 题（每类 4 题）时，很多结论在换题后不成立。于是改用从未用过的 BEAM 100K 留出集（60 题）验证；但之后的诊断和配置选择也反复用了这 60 题，所以它已不再是独立的留出集。第 4 节的留出集分数应看作"开发中的验证"。
- **答题噪声**：同一份读出答两遍能差 3 分，30–40 题的集上两遍之间最多差 9 分。所有比较每组答两遍取平均；改动是否起效，看它针对的题有没有按机制答对。
- **改哪层只重跑哪层**：只改读出就只重跑读出；只改段层就复制原始记录和 SB、清掉段，再续编（一次 80 秒、34 次调用）；只有改了第一步才整套重编。否则 SB 那一步每次输出的随机差异会混进比较里。
- **答题会漂移，比较要同一时段**：同一份读出一字不改，隔几小时重答，60 题从 59.5 变成 57.2；同一份读出答两遍，60 题里 14 题前后不同。几次"改了反而掉分"其实都是在这个范围里。之后的比较都放在同一时段跑，并逐题看针对的题有没有按机制变化，不只看总分。段层每次重跑的输出也差很多（同一提示词三次：61、79、80 段），所以段层的改动要读切分和摘要本身，单次重跑的分数说明不了好坏。

### 3.8 编译层回到冻结的定义

**现象**：换上 mini 套件（AML 公开数据抽样）后，v14 编译暴露出切得过细：LoCoMo（人与人的短句聊天）一条消息一个 SB，打招呼也算，一窗 341 条消息撞上 1.6 万 token 的输出上限，两个窗口全部失败；PersonaMem v1 里人讲一段自己的感受，被逐句切成几十个 SB；人贴进来的文档、群聊导出被逐行当成人的话。60 题的编译要近半小时（1755 秒）。

**原因**：我们在实现里反复改动 SB、段、Line 的层级（SB 被当成"一个点"，段被当成"一件事"），每次压缩上下文后又打一个补丁。

**解决**：把已经说清楚的定义冻结成 `docs/LCE_FROZEN.md`，实现、提示词、读出都照它来：
- SB 是在聊的那件事，一百轮也是一个 SB；用句子主干（谁 + 做了什么 + 哪件事）写理解，不抄具体内容和时间。
- 段摘要写一次、写已经成熟的那一截，结构是前因-谁-何时-做了什么-后果；单独的承接层是多余的，从哪来、引出了什么写在前因和后果里。
- 每窗 2 次调用：SB 一次，段一次。

**效果**（BEAM 100K 留出集 60 题，同一份缓存向量，两遍）：新流程 49.9，v14 + 补位 50.2，打平；编译从 1755 秒降到 237 秒，68 次调用、66 万输入 + 4 万输出 token。LoCoMo 小样本 61.7 对 P1 48.4。

### 3.9 读出：复用 relay，不重新造

- **只挂命中的原文**：SB 变成一件事之后可以跨很多条消息，relay 把一个 SB 的全部来源原文倒出来，LoCoMo 上只有 36.7；改为只挂检索命中的原文，61.7。
- **不补位**（用户定）：证据有两条路就够了，补位的边际收益低，分差在答题波动之内。每题字符降到 P1 的一半左右。
- **全部段摘要**：原来只按相似度给 3 段，而总结、计数类题问的是全局；给全部段摘要后总结题 57 → 75，总分 49.4 → 50.3。
- **晨昏线标记不给答题模型**：长期偏好段还漏着 `[confirmed; before]`，已去掉。
- **SB 数上限截断了原文命中**：读出按"原文命中 + SB 检索"合并排序后只取前 16 个 SB 当锚点，原文命中的 SB 排在 16 名外就连同原文一起丢了——60 题的前 30 条原文命中里丢了 208 条，人的消息 128 条，前 10 名里 12 条。一道时间题的答案原文（"API key obtained on March 10"）在原文检索里排第 3，就这样没了。这个上限是 10-29 在旧编译上定的，换了 SB 粒度和补位方式后没有重查。改为每条原文命中都带出它的 SB（`hit_anchors`）：时间推理两遍都 33 → 50，总分 58.5 → 60.1。
- **命中的原文整条给**：原来按选中 SB 的指针裁剪原文，一条消息切进几个 SB 时只给被选中那个 SB 的部分。BEAM 上实测没丢（一条消息挂多个 SB 的只有 6/632），但贴长文档的数据会多；改为命中的原文整条给。
- **段摘要带位置**（`thread_span`）：定义要求段带首尾消息的时间范围，读出里却只给摘要正文，按相关度排，看不出先后。每条段摘要前加上首尾一步的位置和时间后，事件顺序两遍 54 → 67。
- **段摘要往下钻（试过，关掉）**：让最近的几段再带出它们的 SB 和原文（`drill`），按定义"段摘要辅助检索，再往下定位证据"。但带进来的多是旧值和别的日期，知识更新两遍 67 → 50、时间 50 → 33，默认关。
- **超过 top_k**：AML 规定 Search 最多返回 top_k（正式评测 100）条。长历史的段摘要多达 60 条，加上 Line 片段和 30 条原文会超过 100，原来截掉的是排在最后的原文命中。改为先去掉离问题最远的段摘要。

### 3.10 时间转换和读出用了两套标准

**现象**：读出里写"会话开始于 03-14"，人自己却说"3 月 15 日开会"。

**原因**：本地评测数据的转换脚本用 `datetime.strptime(...).timestamp()`，按转换机器的本地时区解析；运行时按 UTC 显示。BEAM 100K 和 LoCoMo 是在 UTC+8 的机器上转的，所有日期早了一天；BEAM 500K/1M 和 LongMemEval 是在固定 UTC−7 的机器上转的（LME 用题目里原样保留的提问时间交叉验证：提问早于会话的违例从 23 条降到 5 条）。

**解决**：转换统一按 UTC 解析；本地数据全部改正（BEAM 归到当天 0 点，LME −7 小时，LoCoMo +8 小时）；已编译的库改时间、重算请求哈希，只重跑段层（段摘要里写的日期也跟着改正）。这只是本地评测数据的问题，和平台无关，但转换和读出用两套时间标准本身就不该存在。

### 3.11 决策模型旁路

**起点**：矛盾题两边都接近 0——人既说过做了、又说过"从没做过"，两句都在读出里，答题模型只看到一边就答"No"。拒答题则是答题模型把助手的建议当成了人做过的事：问"我执行了哪些 ESLint 规则"，规则清单是助手给的示例，人从没说过。两类都需要在检索之后"理解"一次，而我们不把冲突做成编译产物。

**做法**：Search 时用百炼的决策模型（System One，输出是/否的概率或选择）做旁路，规则在答题前定死：
- 先分流：这题是"问人有没有做过某事"、"问人自己的某个具体信息"，还是其他（60 题里，选成前者的正好是 6 道矛盾题）。
- **矛盾**：对"有没有做过"的题，逐条判断前 30 条原文命中里人的消息是说做过还是说从没做过；两边都有（概率 ≥ 0.5）就在读出最前面引用两句原话。只判断人的消息：决策模型会把助手的话当成人说的。
- **没说过**：对"具体信息"的题，整组判断这个信息是人说过的、只在助手的建议里，还是根本没有；后两种就说明一句。
- 调用在服务的主线程外并行，失败就不加说明。

**效果**（只重答挂上说明的 18 题，其余沿用）：52.6 → 58.5；矛盾 8 → 50，拒答 50 → 67。

**合规，以及"没说过"为什么关掉**：AML 规定 Search 不得生成最终答案，也不得把答案伪装成记忆记录；商业赛道 Add/Search 用模型不受限制，重排器也不受限制。决策模型只输出概率和选择，说明的文字是固定模板加人的原话。矛盾说明是挑证据、排顺序，再加一个"两处说法不一致"的事实标签，没有回答"做没做过"。"没说过"那条说的却是"这个信息不在记录里"，几乎就是拒答题的答案；而且它在 PersonaMem 上 62 题挂了 42 题，大面积误触发。所以它默认关闭（`absence`），只保留矛盾说明。关掉后 PersonaMem 58.1 → 58.9，BEAM 拒答回到约 50。

**另一个 agent 的改写被撤回**：一次没有实测过的改写把缺失判断改成"只看完整消息、合计超过 15000 字符就不判"，把矛盾说明改成"先比较时间与范围"。BEAM 上挂说明的题从 18 道变成 4 道，60 题 60.1 → 55.5。判断规则和措辞已恢复到实测过的版本，限时、健康检查、遵守 Retry-After 这些工程改进保留。旁路现在判断的是读出自己的原文命中（同一个检索文本、包括选项，同样的条数），而不是另起一次检索。

**试过、没用、放弃的**：
- 逐条给 P1 的候选打相关度再重排：留出集 +2.4，换到 mini 套件 −4.2；知识更新被拉低（新旧值都"相关"）。
- 拒答用"人自己有没有给出这个信息"逐条判断、或整组判断"只凭人说的话能不能答"：分不开拒答题和其它题。
- 矛盾说明再加一句"这些消息没有说哪个是定论"：不变，官方提示词要求只输出答案，模型不会反问。
- 多会话：让决策模型挑出相关原文按时间列清单——路由太宽（36/60），挑中的多是带代码的长消息，多会话 33 → 19。
- 拒答改成"检索的最后一道关"，逐条过滤掉"人没说过"的候选，候选删空就等于没有记录：规则上干净（过滤属于检索），但用已有的逐条打分推算，6 道拒答题里 5 道会被过滤空，6 道信息抽取题里也有 4 道会被删光证据，分不开，没有上线。

### 3.12 段的收口

**现象**：一窗结束时最后一段还没收口（看不到后面话题怎么走），留给下一窗判断。下一窗的第二步只问"第一段接不接着它说"（`joins_open`）。不接着说时，没有任何一步给它写摘要，它就从段摘要层消失了（BEAM 上 79 段里约 7 段）。

**弯路**：
- 在第二步里加一个字段，规定"不接着说就给旧段写摘要"。模型因此倾向于说"整窗都接着旧段"，把不同的话题硬并成一段，摘要只写了后半段（例如"部署到 GitHub Pages"从摘要里消失了）。第一版还给这个字段配了填空式的示例，所有摘要都被带成了"Cause: …; who: …"。
- 改成单独补一次摘要调用，规则正确，但每窗多一次调用，增加了复杂度。

**本质**：这一段被放在待切序列的外面当背景，切分规则（话题转到别的路上，段就到此为止）管不到它。后来加的"不接就写摘要"让两个选项一轻一重，模型自然倒向轻的那个。

**解决**：上一窗没收口那一段的 SB 编成 o1…ok，放在序列开头，后面接这一窗的 s1…sn，整串按同一条规则切；o 不许拆开。第一段在 ok 结束，它就是一段普通的已收口段，照常写摘要；延续到 s，就是接着说。`joins_open` 去掉，每窗仍是 2 次调用。三次重跑：34 个窗口每次都一次通过检查，除历史末尾那段外没有漏写摘要的段，并起来的长段摘要也没丢话题。同一时段答两遍：单独补摘要 52.6，放进序列 55.2；总结题 48 / 45 → 63 / 77，因为段摘要现在连 o 一起概括了整段。

### 3.13 遗忘请求

**现象**：PersonaMem 里人会说"Please forget that I watch Hindi YouTube comedians"。这类请求被编成长期指令，堆在读出最前面，答题模型把它当成"远离这一类东西"，连没被要求忘掉的相近偏好也一起回避了（问晚上看什么频道放松，标准答案用的是他喜欢的板球）。

**解决**：遗忘请求从长期指令里单独列出，标题如实写出请求的范围："人要求忘掉的事：每条只管它说的那一件，人说过的其它事照旧"（`forget_scope`）。这是对请求本身范围的描述，不是让答题模型怎么做。PersonaMem-v2 32K 留出集 62 题两遍：LCE 52.4 → 58.1，中性偏好 50 → 64，遗忘题 68（P1 50）。

### 3.14 工程（定版流程）

- **主线程瓶颈**：编译的模型调用原来在服务的主线程上串行，改成生成器协议，存储操作留在主线程、模型调用在外面并行。pm2_32k 编译 1173 秒 → 199 秒。
- **向量不确定**：同一文本两次请求返回的向量不完全一样（余弦约 0.998），跨次比较时读出会抖。加了本地向量缓存（SQLite，按模型、维度、文本哈希），重启重建索引不重复付费，比较也确定了。
- **覆盖检查误判**：模型按规则在停点停下、遇到贴进来的规则书只给提问立 SB、遇到机器日志给空数组，都被"覆盖不到一半"判成坏答案重试三次。改为看停点前最后一条消息有没有覆盖、空数组直接接受。15 份存下来的失败答案回放全部通过。
- **评分截断**：CLBench 的评分理由写到 4000 token 被截断，没写到分数。评分改用单独的 12000 token 后端。

### 3.15 工程（正式评测期间）

Smoke 和 Full 跑在 InstaBox 免费机器上（7.8G 内存、20G 数据盘、每次连续运行最多 480 分钟），公网入口约 20 秒切断请求。下面是正式评测前后暴露并修掉的问题，都只改工程、不改算法。

- **后台编译**：编译放在 Add 里同步做，窗口收口那次 Add 要等 1–3 分钟，被网关切断。改为 Add 存好原文、建好原文索引就返回（AML 要求的"持久化且立刻可检索"），窗口在后台按用户逐个编译；Search 先等这个用户的后台编译一小会儿，到时还没完就用已有结果回答。
- **背压**：平台逐个样本写完就问。一个用户待编译的积压超过 16 万字符时，Add（已入库）等一会儿，还降不下来就返回 503，平台会重试；否则长历史几分钟就写完，问题来时大半还没编。
- **owner 线程**：所有存取串行在一个线程上。Search 和 Add 的向量请求都曾在这个线程上发，一个请求就把所有用户堵住（Smoke 里 Add 最长 27 秒、18 次被切断）。改为在各自的请求线程上先取好向量、写进缓存。
- **SB 向量检索**：Qdrant 本地模式每次查询都给所有用户的全部点打分，再用 Python 逐个按用户过滤，十几万个点时单次约 2.3 秒，16 路并发的 Search 排队超过 20 秒。改为一次扫描按用户分组记下行号，查询只算这个用户的行（排序不变，有测试对照 Qdrant 自己的查询）；15 万点时首次 0.08 秒、之后 2–4 毫秒。
- **等待参数**：`idle_tail` 曾设 5 秒，Add 一慢，定时器就在两次 Add 之间把尾巴编掉，窗口被切碎（Smoke 里窗口数多了一半）；改回 30 秒。Full 中段因流式题每轮都强行收口、等满 15 秒超时，`search_wait` 改成 3 秒、`add_wait` 改成 8 秒。
- **运维**：文件句柄上限 1024 随用户数增长被用满（每个用户的 Line 图常开 3 个 sqlite 文件），调到 65536；向量守卫和编译代理也要同样调。进程曾被内存耗尽杀掉，加 swap；数据盘一度只剩 1.8G，把 swap 移到根分区。机器跑满 480 分钟会被强制暂停并冷却 5–20 分钟，需要在跑满前主动暂停再恢复，重置计时。重启时要把全部原文重新装进内存索引，数据越多越慢（后期约 30 分钟）。

## 5. 局限

- **独立验证还缺**：BEAM 留出集的 60 题在开发中被反复使用；定版流程只在 BEAM 100K 和 PersonaMem-v2 32K 上测过，LME、LoCoMo、CLBench、BEAM 500K/1M 没有用最终代码重测。
- **评测噪声大于多数改动**：同一份读出隔几小时重答差 2.3 分，两遍之间 60 题里 14 题不同；段层每次重跑切出的段数差约 30%。本报告里 3 分以内的差都不下结论，只看针对的题是否按机制变化。
- **知识更新**：3 道题稳定取旧值。新旧值和它们的位置都在读出里，但旧值那条原文的措辞和问题更贴近。
- **拒答**：关掉"没说过"说明后拒答回到约 50；过滤式的做法分不开拒答题和信息抽取题。
- **PersonaMem 上仍低于 P1 的类别**：刻板偏好、反刻板偏好、健康状况，原因未查；敏感信息（隐私）未专门处理。
- **多会话、事件顺序没有解决**：多会话的失分是跨多处计数、比较时答错，以及计数口径模糊；事件顺序的先后都对，丢分在"挑哪几件"（标准答案每个阶段挑一件，模型从头开始挑）。记忆侧试过的办法都没有用。
- 决策模型是预览版（`decision-model-preview`），正式评测期间是否可用、限流如何，不由我们控制；不可用时服务照常，只是不加说明。
- 平台的答题模型比本地用的弱时效果如何，未测。

|---|---|---|---|
| P1@100 | 75.2% | 75.2% | 22.5 万 |
| 定版 LCE | 44.0% | 90.8% | 9.8 万 |
| LCE + 补 40 条原文 | 51.1% | 91.5% | 12.0 万 |
| LCE + 补 70 条原文 | 64.5% | 92.9% | 18.3 万 |

九成证据进了读出，但只有四成以原话进去，摘要题最明显（原文 26.9%，P1 67.2%）。SB 只写主干、细节留在原文，答题模型拿到的是概括。补 P1 的原文补不回来，体积翻倍，还挤掉一半段摘要。两套留出集都没有一题超过 117,760 token（P1 最大约 7.9 万），"被平台截断"在这里不成立。

**时间链路（BEAM 19 道时间题逐层核对，各数据集统计年份）**：
- 读出里的时间只写到月日（`%m-%d %H:%M`），没有年份；官方答题脚本只读 `content`、不读 `created_at`。LoCoMo 留出集 58.6% 的时间题答案要写年份（如"哪一年开始交往"，原话是"三年前"）。补上年份，读出只多 0.69%。
- 没有消息时间的消息标着"会话开始于 04-05"，答题模型当成了消息自己的日期，算出"0 天"（标准 10 天）。
- 段摘要写进了旧计划的数值（截止日期 4 月 1 日，后来改成 4 月 5 日），排在前面，模型选了旧值；违反冻结定义"段摘要不写具体数值"。
- 4 道间隔题数值全对、只得一半分：官方提示词要求"只给答案"，评分细则又要起止日期。这对所有参赛者一样。

### 5.2 设计没有落实到位的地方

| # | 设计 | 实际 | 后果 |
|---|---|---|---|
| 1 | SB 是投影，被检索到时带着它指向的原文精确分块一起给出（冻结文件 §5：命中的原文挂在对应的 SB 下面） | topic 编译不再输出块号（BEAM 100K 定版编译 640 条指针全是整条消息）；定版读出 `raw_of_sb: hits`，经 Line、段摘要找到的 SB 一条原文都不带；原文命中是单独的条目，没挂在 SB 下面 | 九成证据只以 SB 概括出现；要细节、要集合、要全局的题（A3、B3、F1、C2）失分 |
| 2 | 双时间轴：读出里每条原文带着它的消息时间 | 时间格式丢了年份 | 问年份、跨年间隔的题无解 |
| 3 | 不把会话时间当成事件时间 | "会话开始于"标在会话里每条无时间消息上 | 答题模型把它当成消息的日期 |
| 4 | 段摘要只写前因-谁-何时-做什么-后果，不写数值和细节 | 编译模型把起点、目标、计划日期写进段摘要 | 知识更新题选旧值 |
| 5 | LCE 滞后编译，等自然的语义断点 | 比赛里每次 Search 都强行收口（`compile_before_search`） | 流式题窗口被切碎（平均每窗不到 3 条消息）、每轮都在等编译，Full 中段大面积超时 |
| 6 | 读出按问题分配原文和投影的比例 | 原文名额固定 30 条，不看历史长短 | 短历史上不如 P1（P1 的 100 条几乎就是整段历史） |

## 6. 取舍与后续方向

下面是为了比赛、受限于工程条件或时间而做的取舍。它们不是设计上认为对的终点，而是以后升级和继续开发的起点。

### 6.1 比赛规则带来的取舍

| 取舍 | 原因 | 以后的方向 |
|---|---|---|
| 不给答题模型任何"怎么答"的提示，长期指令只作为记录交出去 | 答题提示词由平台锁定（"只用上下文、直接简洁、不要解释"），记忆侧写指令属于 prompt injection | 在自己的产品里，长期指令和偏好直接进入回答侧的系统设定，不再和"不要解释"这类外部约束冲突 |
| "没说过"的判断关掉，决策旁路只留矛盾说明 | AML 规定 Search 不得生成最终答案；"信息不在记录里"几乎就是拒答题的答案 | 在产品里，这个判断可以直接交给 agent 决定"先问用户"还是"说不知道"；比赛里可再试纯过滤式的做法，但要先有能分开拒答和信息抽取的判断 |
| 段摘要最多 60 条、超过 top_k 时先去掉最远的段摘要 | 每题最多返回 100 条，超出即判不合规 | 段摘要按 Line 分层合并（一条 Line 一条提纲），用更少的条数覆盖全程；按问题动态分配段摘要与原文的条数 |
| Search 前补编尾巴窗口（已改为后台编译，见 3.15） | 平台不调用 flush，结果必须在 Search 时可用 | Search 不再强行收口：没到自然断点的结尾直接交给原文检索（见 5.2 第 5 条） |
| 只用平台给的消息时间，BEAM 会话内的事件没有日期 | BEAM 只在每次会话第一条消息上有时间；双时间轴不编造时间 | 真实对话每条消息都有时间戳，时间推理会是 LCE 的强项；本地评测可另外构造带完整时间戳的数据 |
| 答题模型的强弱只能本地模拟 | 平台锁定 Qwen3-14B，本地没有可用接口 | 用同等规模的模型做读出的控制变量，研究弱答题模型需要什么样的读出（更短、顺序更强） |

### 6.2 工程条件带来的取舍

| 取舍 | 原因 | 以后的方向 |
|---|---|---|
| 决策旁路用百炼预览版 `decision-model-preview`，总等待上限 15 秒，失败就不加说明 | 现成、免费、判断快；但可用性和限流不由我们控制 | 用自己的小分类器或规则替代，或在编译时就留下"同一件事正反两种说法"的索引（仍不做冲突标注，只做可检索） |
| 段摘要里仍会写起点和目标这类数值 | 编译模型 ds1017 不严格遵守"只写结果数值"的规则；改提示词会牵动所有摘要 | 编译后做轻量检查（例如数值是否为结果），或换更守规则的编译模型；知识更新题的旧值干扰会随之减少 |
| 段层每次重跑差别大（同一提示词 61–94 段） | 温度为 0 仍不确定；段的切分本身是判断 | 用更明确的切分锚点（会话、长停顿、做的事变了）先切一刀，模型只在锚点之间判断；或多次切分取一致的边界 |
| 知识更新：新旧值都交出去，由答题模型挑 | 冻结定义：冲突不做编译产物，记忆只做诚实召回 | 用晨昏线已有的"后来落定"（`settles`）和时间轴，把同一件事的先后在读出里按时间排在一起，让"最新"一眼可见，而不是给出结论 |
| 遗忘请求靠 SB 文字里的关键词（forget / 忘掉）识别 | 不改第一步提示词就能做；改提示词要整套重编、风险大 | 在第一步给遗忘请求一个明确标记；真正的遗忘语义（记得"要遗忘"本身还算不算记得）留待 MR 的记忆治理设计 |
| 段摘要命中后不往下钻到 SB 和原文（`drill` 关） | 下钻带进了旧值和别的日期，知识更新和时间题变差 | 下钻时按时间只取最新的那几步，或只取问题指向的那一步 |
| 人在消息里贴整段文档、群聊导出时，第一步可能逐行切、撞 1.6 万输出上限，重试后该窗只留原文 | 识别"贴进来的材料"的规则会影响所有聊天数据集，没来得及整套重验 | 按上下文识别转贴（材料本身不立 SB，只立"人贴了什么、为什么"），并在全部数据集上重验 |
| 向量接口同一文本两次返回略有不同，加了本地缓存 | 不缓存时检索会抖、比较不确定 | 缓存保留；换向量模型时缓存按模型分开 |

### 6.3 时间带来的取舍

| 取舍 | 原因 | 以后的方向 |
|---|---|---|
| 定版流程只在 BEAM 100K 和 PersonaMem-v2 32K 上测过 | 提交在即，来不及整套重跑 | 用最终代码重跑 LME、LoCoMo、CLBench、BEAM 500K/1M、PM1，并在没参与调整的数据上做独立验证 |
| 正式评测的总耗时和费用没有估算 | 不知道正式题库的总量 | 按"每历史字符约 1.2 个输入 token"、单路每分钟约 2–3 万字符估算，部署前按并行度算好 |
| 比较只做两遍、60 题 | 每组答题要几分钟，晚上的大部分比较都在噪声范围里 | 加题量、加遍数，固定同一时段答对照组；建立"同一读出重答"的噪声基准 |
| 多会话计数、事件顺序挑选没解决 | 问题在于计数口径和"挑哪几件"，记忆侧试过的办法都无效 | 段摘要分层（一条 Line 的提纲 + 各段），让答题模型能按阶段挑；计数题需要的同类事项，按 Line 聚合后给出 |
| PersonaMem 上刻板偏好、反刻板偏好、健康状况低于 P1，敏感信息没专门处理 | 只在一份留出集上看了总分和类别，没逐题查 | 逐题看读出里缺了什么；敏感信息属于"认知安全与隐私"维度，需要单独的设计 |
| LCE 在比赛里只用了 Path A（Line、段）和 Thread，没有用 Path B（跨线假设）和"面" | 比赛的题目以回忆为主；Path B 还在设计中 | 在 MR 中接上 Path B 和"面"，把灵感、跨领域的相同底层逻辑也纳入记忆 |

### 6.4 下一步：改动和尝试方向（11-02 复盘后）

按"先确定、后试验"排。每一步先在本地公开数据上测证据覆盖（不花钱），有效再做小样本答题。

**确定要改的（不需要再验证机制）**
1. 读出时间带上年份（`_when`）；段摘要的首尾位置同样带年份。
2. Search 不再强行收口：只等正在进行的编译，结尾的新消息交给原文检索。流式题不再被切碎，每轮也不用等。
3. 工程：启动时不必把全部原文重新装进内存（按用户懒加载，或持久化索引），常开的 sqlite 按最近使用关闭；减少 owner 线程上的工作。

**已实现、在测的**
4. SB 挂着它投影的原文一起返回（`line_read.sb_raw`，默认关）：每个 SB 条目在概括后面附上它指针指向的原话，原文检索的 30 条照旧；挂在条目里，不占 top_k 条数。BEAM 100K 留出集原话召回 51.8% → 89.4%（P1@100 79.4%；摘要题 38.8% → 91.0%，事件顺序 40.7% → 88.9%），PM2-32K 65.9% → 98.2%；体积每题约 7.3 万 token、最多 9.5 万，没有超限，但余量不大。待做：预算改成按整份读出算；用弱答题模型做小样本答题，看 7–9 万 token 的读出吃不吃得下。
5. 块号在编译时给出（`compile_input.blocks`，默认关）：第一步写出 SB 来自哪几段，字符区间算在原文上；压缩改成逐段裁短，段号和原文对应。真实窗口各一个：PM2 指向的原文省 27%，BEAM、CLBench 不省（一问一答讲同一件事，整条就是对的；贴进来的文档归到一个 SB）。块号解决一条消息里有几件事，解决不了一个 SB 下面原文太长。
6. 读出时按问题挑段（`line_read.sb_raw_paras`，默认关）：BEAM 留出集 k=5 原话召回 124/141（整条 126、P1@100 112），每题平均 5.2 万 token（整条 7.3 万、P1 5.6 万）。还没有答题验证。

**要用户先定的（涉及冻结定义或已定的规则）**
7. "会话开始于"的写法：只标在会话第一条消息上，或改成不会被当成消息日期的说法。
8. 段摘要里的数值：编译后检查、或在读出时只用最新的一段，减少旧值干扰。
9. 事件顺序与全局摘要（C2、F1）：在 sb_raw 之后再看，是 SB 粒度和题目要的步骤对不上，还是缺一条 Line 级的提纲。

**尝试方向**
10. 弱答题模型下的读出：用与平台同级别的小模型，只在上面这些题型上对照"原话多一点"还是"整理过的多一点"、更短还是更长。
11. 按历史长短分配原文名额：短历史几乎全给原文，长历史才靠投影压缩。
12. CLBench 类（G3、G4）：文档、规则书整段贴进来的样本，确认读出里文档完整、没有被切碎或截断；这一类主要考答题模型，记忆侧只需要不丢。
13. 遗忘（D3）：本地 PM2 上 forget_scope 后遗忘题 68，Full 上 20，要在 PM2-128K 等更长的数据上复查。
14. 用最终代码在 LME、LoCoMo、CLBench、BEAM 500K/1M 上整套重测，建立独立于留出集的验证。
