# 配置说明：每项开不开、效果、成本

这份说明讲 `mr_mem_aml` 的每个配置项：建不建议开、实测效果、成本，以及数字的出处。

**开发基线**是 `deploy/runtime.server.json`，内容和 `examples/runtime.aml-lce.json` 相同。代码里的默认值和这份基线不完全一样，下文的"基线"一栏指配置文件里的取值。

**怎么看这些数字：**
- 同一份读出答两遍，分数可以差 3 分，几十道题的小集合上差 5–10 分也常见。所以每组都答两遍取平均；平均差在 3 分以内，算没有差别。
- 出处写成"待办 x.y"的，指 `mrmem-eval/local/LCE_OPEN_ITEMS.md` 里的那一行；写日期的，指同一文件或 `docs/LCE_DESIGN.md` 里当天的记录。
- 编译只有一条路径（冻结定义 §2，11-07 清理）：每个窗口两次模型调用，第一步写 SB，段层切段并写摘要。以前的 flat 引擎、`lines`/`points`/`entries` 放置方式、`slim4` 第一步、`steps` 第二层都已从代码中删除，需要时在 git 历史里找。

## 1. 编译（写入侧）

| 配置项 | 基线 | 建议 | 实测效果 | 成本 |
|---|---|---|---|---|
| `compiler` | qwenplan 的 `deepseek-v4.1-flash-1017`，关思考 | 用它 | 10-31 编译模型对比（BEAM 100K 一段历史 200 条消息、20 题）：端到端 60.8，qwen3.8-flash 55.3；第一步读不出 JSON 的次数 1/13 对 9/21 | 编译 1215 秒、49 次调用、输入 46.3 万 token（qwen3.8-flash 2209 秒、57 次、64.1 万） |
| `scene` | `chat` | 评测用 `chat`；`work` 留给 MR 的 Agent 工作场景 | `chat`：按在聊的那件事切 SB（冻结 §1）。`work`：Agent 汇报 → 人的反馈或决策，是 10-24 的提示词，**没有按冻结定义更新，也没有测过** | 一样 |
| `compile_window.soft` / `hard` / `measure` | 40000 / 80000 / `chars` | 照基线 | 窗口在 soft 之后的第一个自然断点收口，最迟到 hard。模型可以停在 SB 收口处，没编完的尾巴进下一窗（设计稿 4.7） | 窗口越大，固定提示的占比越低 |
| `compile_window.max_messages` | 200 | 开 | 11-01：一窗 500 条短消息时，第一步输出三次超过 16000 token，只留下了原文；设上限后不再发生 | 无 |
| `compile_window.max_chars_per_user` | 1000 万 | 按预算定 | 一个用户超过这个量后只存原文，可以像 P1 那样检索。BEAM 10M 这类历史约占文本赛道三分之一的 token，只占约 3% 的题 | 防止少数长历史吃掉预算 |
| `compile_window.gap_minutes` | 120（代码默认） | 照默认 | 停顿超过这个时长算断点 | 无 |
| `compile_window.count_read` | 关 | **不开** | 11-01 BEAM 100K：窗口 34 → 11 个，输入 −33%，输出 −28%；但段切得更粗（81 → 52），两遍都是 50.9 → 46.5 | 省钱但掉分 |
| `compile_input.assistant_head` | 600 | 开 | 助手每条消息只读开头和结尾共 600 字符，代码块只读前 200 字符；检索和读出仍用全文。BEAM 100K 两遍 50.1 → 50.9（不掉分） | 输入 token −65%，输出 −29% |
| `compile_input.blocks` | 开（聊天场景默认开） | 开 | 第一步写出每个 SB 来自消息的哪几段，读出时只取这几段。PM2 上挂载的原文少了 27%；BEAM 一问一答都在讲同一件事，整条挂载本来就对，体积不变（11-05） | 提示词多一条规则，输出略长 |
| `context_messages` | 20（代码默认） | 照默认 | 同一会话之前的消息只作上下文，不可引用；实际只取最后 6 条 | 输入略增 |
| `compile_concurrency` | 8 | 按端点限流定 | 不同用户之间并行，同一用户串行 | 并发越高越快，注意 429 |
| `keep_raw_on_compile_failure` | 开 | 开 | 重试后仍失败的窗口只留原文、计数，Add 照常返回 200（AML 契约） | 无 |
| `skip_rejected_compiles` | 开 | 开 | 模型端永久拒绝（4xx，如内容审核）时只留原文、计数 | 无 |

**编译成本参考：**
- 平台冒烟测试实测每百万字符 ¥0.9–1.0（窗口小，固定提示的占比高）；BEAM 100K 窗口大，约每百万字符 ¥0.3（11-01）。
- LoCoMo 小集一段历史 629 条消息：4 次调用，输入约 4 万 token，输出约 1.3 万 token（11-06）。

## 2. 后台编译与 Search 时机

| 配置项 | 基线 | 建议 | 实测效果 | 成本 |
|---|---|---|---|---|
| `background_compile` | 开 | 网关会切断长请求时开（InstaBox 约 20 秒） | Add 存好原文、建好索引就返回，到期的窗口在后台按用户编译（11-01） | 无 |
| `background_compile.search_wait` | 15 秒 | 照基线 | Search 最多等这么久，让这个用户正在进行的编译跑完 | 拉长 Search 延迟 |
| `background_compile.idle_tail` | 30 秒 | 照基线，**不要调小** | 11-01 一度改成 5 秒：Add 要 5–7 秒，尾巴定时器在两次 Add 之间触发，窗口被切碎（34 → 53 个，一个用户 2 → 8 个窗），冒烟测试 57.26 | 无 |
| `background_compile.max_backlog` / `add_wait` | 160000 / 12 | 平台连续 Add 时开 | 积压超过 16 万字符时，Add 等待后返回 503，由平台重试（AML 最多 32 次） | 拖慢写入，换来编译跟得上 |
| `background_compile.search_closes_tail` | 未写（= 开） | 待定 | 关掉后 Search 不再强行收口编译，只等正在进行的编译（冻结 §4.7"滞后编译"）。Full 上流式题窗口被切碎（平均每窗不到 3 条消息），原因就是每次 Search 都强行收口。离线评测测不出效果（11-05） | 无 |
| `compile_before_search` | 开 | 开 | Search 前先编完这个用户剩下的内容（或等后台编译） | Search 变慢 |

## 6. 决策旁路 `decision`

| 配置项 | 基线 | 建议 | 实测效果 | 成本 |
|---|---|---|---|---|
| `decision` | 开（token plan 的 `decision-model-preview`） | **合规待定** | 决策模型看问题和原文命中，必要时在最前面放一条说明（人前后说法不一致）。说明 56.8 / 关 51.9 / 只排序 52.3（10-31）：增益全来自"人自己的说法不一致"这句判断，而这句正是 BEAM 矛盾题标准答案的核心句。"没说过"说明默认关：PM2 62 题挂了 42 题，关掉后刻板偏好 40 → 60。AML 规定 Search 不得生成最终答案；这条说明算不算，要用户定 | 每题一次决策调用，进程内 16 路并发 |

用户的决定是：重排测试没有增益的不进定版，但接口和脚本保留，等新用法（记忆"决策模型旁路保留"）。

## 7. 已删除的配置项（11-07）

`path_a_engine`、`placement`、`place_policy`、`step1`、`layer2`、`line_policy`、`step_policy`、`assistant_policy`、`lce_enabled`。配置文件里还写着这些字段时会加载失败，删掉即可。`step1` 现在由 `scene` 决定：聊天场景用 topic，工作场景用 moves。`compile_window` 变成必有项，代码默认 40000 / 80000 字符。
